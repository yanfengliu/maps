## R33 — P1: package backup and rollback do not enforce the required no-reparse boundary

**Locations:** `support_contract.py:15–28`; `run_native_support.py:14,20–35,65–68,83–90,193–204`; `support_collision_tools.py:15`.

The source helper checks each component beneath `project`, but never inspects the project root or its ancestors. Both wrapper and native helper derive roots with `resolve()`, which hides that a root was reached through a link. More importantly, package enumeration, hashing, backup copying, backup reads, restoration and removal do not call this helper or any equivalent ancestor guard. `asset_files()` uses recursive enumeration, and backup/restore uses direct `copyfile` and `unlink`. A linked asset leaf is hashed and copied by following it; a junction ancestor of `Content`, an affected package, or the retained backup directory can redirect restoration outside the intended real project tree. The final digest comparison is after the write and cannot confine it. This is directly within the requested recoverable, exactly owned package rollback boundary.

**Required repair:** preserve and validate the lexical absolute root; reject existing reparse points at every root ancestor and descendant/leaf before enumeration, read, backup creation, restore, deletion and report write. Validate allowed package and sidecar paths against the same root, propagate inspection/enumeration errors, and verify backup bytes before using them. Revalidate immediately at each filesystem operation rather than relying only on an earlier source-file check. Keep rollback limited to the observed allowed packages and refuse it when confinement cannot be established. Exercise safe owned parent/leaf junction controls for admission and rollback, proving no outside write; no such control was run by this reviewer. The existing path unit only checks a parent-traversal string and digest/size mismatch, not these junction/write cases.

## R34 — P2: input size is checked after an unbounded allocation

**Locations:** `support_contract.py:31–44,49,60,74`; related receipt read at `run_native_support.py:68` and whole-file hashing at `:20–29`.

`check_record` calls `read_bytes()` before checking that `bytes` is an integer or equals the actual length; it has no maximum admitted size. The manifest itself is also read without a cap before its hash is checked. A stale or malformed oversized GLB, JSON ray fixture or manifest can therefore allocate its entire contents before the intended refusal, even if its receipt says it should be small. The helper also directly reads base/photo JSON and the apply receipt. Exact final hashes do not provide preallocation bounds.

**Required repair:** validate a positive integral declared size and an explicit appropriate upper bound before opening/allocating, compare stat and opened size, use bounded exact reads for JSON, and stream hashes/copies for large admitted binary packages where appropriate. Keep the source limits consistent with the final reviewed producer output; do not silently lower a valid source's limit to hide an incompatibility. Reject growth/read errors and give the input path. A sparse/oversized control must demonstrate refusal before allocation; current units only demonstrate rejection after reading a six-byte fixture. No large-read control was executed here.

## R35 — P1: descendant discovery does not establish exact process ownership, and cleanup failure can skip rollback reporting

**Locations:** `run_native_support.py:102–114,137,150–176,188–212`; inherited `mcp_run.py:371–380`.

`census_owned()` rebuilds ancestry from the editor's numeric PID and `ParentProcessId` alone, then stores the current child rows as owned. Comparing a later row's `CreationDate` to that stored row does not validate the original discovery. A concrete stale-parent condition is: an unrelated process with PID P exits leaving a live child; a new genuinely owned editor helper reuses P; the census follows root → new helper P → the old unrelated child because that child's recorded parent ID is still P. No parent/child creation-order check rejects it. The current child creation date is then stored as ownership evidence, so the later `taskkill /PID ... /T /F` can kill it. This finding does not rely on reuse of the editor PID while Python retains its process handle.

Conversely, discovery happens only after tool registration and around the long operation. If an intermediate helper exits before a census, its live grandchild is not reachable from the then-current rows. That process can remain absent from `owned_children`; `cleanup_verified` can still become true and allow package rollback while an owned descendant survives. The fourteen offline tests do not launch or verify this new wrapper's process tree.

There is also a reachable cleanup failure gap: the call to `stop_owned_tree(process)` at line159 is outside the subsequent cleanup exception guard. Its Windows `taskkill` has no subprocess timeout; if it hangs, raises, or its following wait times out, execution escapes the rest of the finally block, including descendant verification, rollback disposition and the terminal receipt. A finite native startup/tool timeout does not cover this path.

**Required repair:** establish ownership from launch with durable process identity/owned containment and preserve it across early parent exit; do not acquire new ownership from a bare stale PPID chain. Never terminate a row merely because it was just discovered by that chain. Apply finite deadlines to every cleanup operation, catch cleanup failures while still preserving a terminal failure receipt, and permit rollback only after the complete owned set is confirmed stopped. Prove early-child/early-parent-exit cleanup, reused/stale-parent identity refusal, and cleanup-error reporting using bounded owned controls. These are static findings; no process was terminated or ownership mutation run by the reviewer.

## R36 — P2: support frame and version types are not admitted before mutation

**Location:** `support_contract.py:39–96`, especially `:45` and `:75`; caller `support_collision_tools.py:114–125`.

`read_contract` never reads the support manifest's `frame` object. It checks only the ray fixture's ENU frame. A correctly hashed manifest declaring a different GLB/runtime/Unreal axis or unit contract can therefore reach import, collision edits and terrain replacement, which continue using hardcoded conversion assumptions. The agreed support interface requires `metres-Xeast-Yup-Znorth`, `metres-Xeast-Ynorth-Zup` and `centimetres-Xeast-Ynorth-Zup` respectively. Hashing a document proves which document was read, not that its declared frame matches those assumptions.

The version checks also use Python equality alone: `True != 1` is false, so `schema_version: true` passes for both the manifest and ray document. Python dictionary equality for origin/datum does not by itself enforce exact scalar types either. This consumer needs its own typed contract admission; R31 in review33 covers the separate C++ runtime consumer and does not repair this code.

**Required repair:** check actual version types and the complete agreed frame fields before backup/native launch, and compare required structured origin/datum values with type-aware semantics. Preserve the existing exact valid source records and geometry. Include missing/wrong frame and boolean-version controls at the production contract reader. These failures were reasoned from the frozen code, not run through a native editor.
