## Checked policy and implementation

The root's explicit policy change is consistent with the primary API contract. Microsoft documents that ordinary Job completion notifications are not guaranteed and that a notification PID may be recycled unless its process handle remains open. A missing EXIT notification therefore cannot establish a live process by itself. [Microsoft Job completion-port contract](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port).

The physical check must establish the state of the retained process object separately. A zero-time wait distinguishes a signaled object from timeout/failure; the exit-code query must itself succeed. A code of 259 alone is ambiguous because an application can also terminate with that value. V3 checks the wait result and query success independently. [Microsoft WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject), [Microsoft GetExitCodeProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess).

- **Exact membership before identity.** `run_owned_game.py:103-125` opens or accepts the process handle, calls `IsProcessInJob` against the exact still-open Job, requires API success and true membership, requires an unsignaled live handle at admission, then obtains creation FILETIME and image identity through that same handle. Foreign, unavailable, already-exited and failed-query admissions are refused. The suspended primary is assigned, retained and observed in that Job before resume at lines 221-226. The underlying helper uses a hidden suspended CreateProcess launch, a restricted inheritance list and an owned kill-on-close Job; it does not infer authority from a numeric PID or parent chain.
- **Observed primary-thread close.** `resume_with_observed_thread_close` at lines 51-58 checks the one-time resume transition and records the actual `CloseHandle` return. It marks the thread handle absent only after successful closure. Cleanup records this observation at lines 171-174 and checks any still-held thread directly. A normal successful path no longer infers closure merely from a `None` field.
- **Physical termination and complete denominator.** Cleanup obtains final native Job membership and accounting before iterating every retained member at lines 157-165. It uses each original held member handle, with the primary's held creation handle as the explicit fallback. `held_termination` at lines 67-73 requires `WaitForSingleObject(handle,0)==WAIT_OBJECT_0` and successful `GetExitCodeProcess`; 259 does not decide termination. `ownership_local_ready` at lines 75-90 requires final membership `[]`, active accounting 0, unique retained identities equal to native TotalProcesses, one matching termination observation for every identity, successful exact-Job admissions, no observer error, a post-quiescence empty queue poll, every relevant handle closure, and cleanup within 15 seconds. Omitting an identity or query result cannot become a local pass.
- **Notifications remain evidence, not manufactured proof.** The observer retains received messages at lines 128-141. Cleanup records the actual ledger, reconciliation flag, ACTIVE_ZERO observation, missing EXIT identities and empty-poll bound at lines 166-167. Local physical readiness does not require a complete EXIT ledger, and it does not set an incomplete ledger to complete. The empty poll is explicitly limited to queued observations; it does not assert that a delayed or dropped notification must have arrived.
