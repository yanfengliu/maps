## Reviewers and coverage

One independent reviewer, read-only, which did not build any part of the work.

Actual access: the full working tree and all recorded evidence. The reviewer ran fast read-only Python over the JSON records and derived the frame mapping independently from first principles rather than from the documents.

Missing coverage, stated by the reviewer: it ran no Unreal editor and no Blender, because the orchestrator was running the full pipeline on the same machine and a second editor or Blender would have collided. So every finding about engine behaviour is reasoned from source and recorded evidence rather than demonstrated in-engine, and the reviewer marked confidence accordingly. No second reviewer and no multi-CLI round: the change is substantial but carries none of the high-risk markers in the fleet canon — no persistence, migration, security, auth, concurrency, money or supply-chain surface, and nothing outside this repository.

## Reports

### Independent reviewer

Verdict: the geometry, the frame mapping and the layout and asset gates are genuinely well built and could not be broken. The weak spots are in what the gates *claim* versus what they *execute*, plus two defects in the documented user flow. Five findings would actually bite.

**Genuinely broken.**

*F1, high confidence — neither documented way to see the town shows the town.* `Config/DefaultEngine.ini:2-3` sets `EditorStartupMap` and `GameDefaultMap` to `/Engine/Maps/Entry.Entry`, and nothing anywhere points either at `/Game/Maps/MedievalCity`; the only other map reference is `+MapsToCook` in `Config/DefaultGame.ini:11`. So the README's "open `MedievalCity.uproject` and press Play" opens the engine's near-empty map, and `AMedievalGameMode::FindPlayerStart_Implementation` (`MedievalGameMode.cpp:16-34`) drops the character at the fallback `FVector(0,0,200)`. `plan.md` states the outcome as a project that "opens into a walled medieval town"; as configured it does not. Compounding it, the README also offers `run_probe.py`, which defaults to `--mode smoke` (`run_probe.py:246`) and loads `/Engine/Maps/Entry` with the probe's own test floor and cube wall. Every piece of town evidence came from `--mode city`, which the README never named. A reader following the README twice never sees the city.

*F2, high confidence on the reasoning, not demonstrated in-engine — the camera-mode measurement would be identical if the camera switch were deleted.* `MedievalCharacter.cpp:216-229`: all three active-camera accessors branch on the private `bFirstPerson`, the same bool `IsFirstPerson()` returns. Both camera components are attached to the capsule and carry valid world transforms regardless of activation. Deleting `MedievalCharacter.cpp:198-199`, the two `SetActive` calls that actually change the rendered view, would leave `bFirstPerson` flipping, the avatar hiding, and `camera_separation_cm` still reading about 350 cm, because the 320 cm spring arm is a geometric fact independent of activation. The gate would pass with the camera mode broken, and only a human comparing the two captures would notice. This is the fleet rule that a check built from its checked symbol proves only self-agreement, and it sits under exactly the criterion the probe is supposed to settle. The controller's real view is one call away: `PlayerCameraManager->GetCameraLocation()`, or `CalcCamera`.

*F3, high confidence — the triangle check the contracts say the gates require does not exist.* `level_build_editor.py:308-309` and `import_assets_editor.py:263-266` record `triangles` and `inventory_triangles` side by side and never compare them; `import_assets_editor.py:267` fails only on `triangles <= 0`. The sole guard against decimated geometry is reading the Nanite setting. `design.md` says both counts matching "is what the bounds and triangle checks require", and `build_level.py:49-57` prints a `tris`/`inv` column pair as though checked. Any other route to a decimated LOD0 — import reduction settings, a future Interchange default, a build-settings change — passes both gates silently while a character walks on half-resolution collision geometry. Every count matches in the current run, so this is a missing guard rather than a wrong value.

*F4, high confidence on the logs — the native build gate's evidence shows no compile of the Editor target.* `artifacts/medieval/build/MedievalCityEditor-Development.log` contains one action, `WriteMetadata`, and names the engine's own `UnrealEditor.exe` as the output binary; the game log has one link and no compiles. `build_native.json` nonetheless records `up_to_date: false`, because `build_native.py:153` tests only for the literal "Target is up to date", which UnrealBuildTool did not print. The gate then asserts only that the runtime DLL exists, with no mtime or source comparison, and prints "built". The binaries are probably current, since UBT's own dependency analysis decided nothing needed doing, but the stated bound — that the gate proves both targets compile and link — is not what the evidence shows, and there is no clean or rebuild path that would produce that evidence.

*F5, high confidence — the level gate's "no undeclared actor is present" is narrower than its stated bound.* `level_build_editor.py:429-436` fails on undeclared StaticMeshActors only; every other undeclared class lands in `other_actors`, reported and never failed. `check_world_actors` does catch duplicates of the five tracked world classes, so the hole is a stray actor of any other class — a saved probe actor, a camera, a note, a brush. Given this branch's own history, a probe saving eight actors into the engine's default map, stray actors are the live defect class here, and `build_level.py:7-8` says the case is covered.

**Weaker claims and latent flakiness.**

*F6 — "injects W, A, S, D" is false; only W is injected.* Every `EKeys::` in the probe is `W`, `V`, `LeftShift`, `SpaceBar`, `MouseX` or `MouseY`. `plan.md` claims all four movement keys and the README tells users to walk with them. It matters beyond wording: the three unexercised mappings carry the modifier machinery (`MedievalCharacter.cpp:323-333` — S is swizzle plus negate, A is negate, D is bare), which is precisely the bug class a key-injecting probe exists to catch. `design.md` describes the sequence without A, S and D, so the code follows the contract and `plan.md`, the acceptance document, is what overclaims.

*F7 — the wall-collision step can pass by being stuck from the start.* The probe holds W for an approach then a push, and asserts only that the push moved no more than the limit. Nothing asserts the character moved during the approach and nothing confirms contact, so a capsule inside geometry, or one whose movement had already broken, records about zero push and passes: "walking into a wall stopped it" would be satisfied by never having walked. The recorded run behaved correctly, 325.8 cm then 2.5 cm, and the approach distance is already in `probe.json`.

*F8 — the two three-second walks consume more clear street than the layout gate promises.* `test_layout.py` guarantees 12 m of clear street; the probe walks 872 cm, toggles camera, then walks another 874 cm from where the first ended without repositioning, 17.5 m in total. This layout has about 39 m of clear main street so it worked, but a layout at the guaranteed minimum would stop short and fail. A false red rather than a false green, but the probe depends on slack no gate guarantees.

*F9 — one of the probe harness's RHI instruments never fires.* `run_probe.py:55` matches `Initializing (?:FD3D12|D3D12|Vulkan|OpenGL)`, while the engine logs `LogRHI: Using Default RHI: D3D12`, so `run_probe.json` records `rhi = None`; `level_editor_session.py:47` keeps a pattern that does match. Since one pattern in that dict is demonstrably wrong for this engine, the sibling NullRHI pattern has never been shown to fire either, and the harness raises a problem on it. The verdict is still sound because the live check reads `GDynamicRHI->GetName()` out of `probe.json`, but that is one working instrument and one dead one.

*F10 — one harness threshold is read from the artifact under test.* `run_probe.py:227` takes `sprint_required_ratio` from `probe.json`, which the compiled probe wrote, while every other re-check pins its own constant. Not a hole today, since the same binary writes both sides, but it is the one place the independent re-read defers to the thing it re-reads.

*F11 — the asset gate reads declared accessor bounds, not vertices, for its envelope checks.* `test_assets.py:132-139` reads `accessor["min"]/["max"]`, and the footprint, height, footprint centre and `min_z` are built from them. The docstring says every measurement is read out of the exported .glb rather than from the generator's numbers, which is true in that Blender's exporter writes those fields, but they remain declared metadata. A mesh whose accessor bounds disagreed with its vertices would pass. The flat-box check does read real vertices. Low risk; the bound reads stronger than it is.

*F12 — the layout gate's determinism re-run has no timeout.* `test_layout.py:729-735` calls `subprocess.run` twice with no `timeout=`, so a hanging generator hangs the gate; `test_assets.py:245` gets this right for the equivalent rebuild.

*F13 — the walkable-path-through-the-gate claim is 2D, assumes the arch, and nothing walks through it.* `test_layout.py:18-20` says so honestly: the inventory does not record the opening, and the check takes the 3.0 m arch on trust from the asset generator's own build-time assertion. The runtime probe never reaches the gate — its walks cover layout y 3 to about 20.5 while the gate sits at about y 42.6 — and the gate vantages are direct placements explicitly flagged as not control evidence. The criterion is met as written, but no evidence exists that the gate is passable in the engine.

*F14, medium-high confidence — the level gate traces a different collision channel from the one the character walks on.* `level_build_editor.py:122-125` uses Visibility for the axis-sign probes and for the ground-under-player-start check, while the in-game probe measures clearance on `ECC_WorldStatic`. A mesh can answer one and not the other, so "there is ground under the player start... for a character to stand on" claims more than a visibility trace shows. The runtime probe does prove standing, so combined coverage is fine; the individual bound is overstated.

*F15, medium confidence — the final repository-gate record shows no `npm test` output.* The early log shows all four green with 51 passing; the final log has output for build, typecheck and audit and an empty test section. The tracked diff touches no product code, so the real risk is near zero, but the final record does not show the test gate running. Separately, `integration-run.sh` runs the nine medieval steps and no npm gate, so the script documenting the integration run does not cover that criterion at all.

**Untidy, not broken.** A dead `Step.Name != "capture_jump"` condition, no step having that name. An unused `GetRightArmPitch()`. `PlaceCharacter` writing `ground_clearance_min_cm: 0` and `max: 0` into placement rows as though measured. A guard that can only be false when `player_start_m` is absent, working by accident and leaving no note when it skips. A settle-stage comment that overstates which envelope its samples are excluded from. A session timeout message that says the editor wrote no report when the report was written and only the process overran. A recorded `exit_code` that is never tested. The ambiguous prose `-(t+90)` in `design.md`, read two ways, on the one number already got wrong once. A whole-PNG copy made purely to narrow a type. No devlog line and no lessons change yet. And a tension worth naming: the red-run proofs the plan cites live under ignored paths, so nobody can re-run them from the repository.

**What the reviewer tried to break and could not.** The frame mapping, derived independently and then checked against every live number in `probe.json` — all seven vantages, the player start, the paced-run start and the wall-run start match `(100x, -100y, 100z)` and `-(t+90)` exactly, each vantage capsule sits exactly 72 cm below its camera, and the wall run physically ends against the ring at x about 56. The axis-sign probes, which ask the imported geometry where it is rather than agreeing with the transforms the same script wrote, with every other actor ignored so a hit can only be the measured mesh. The asset gate's parsing of the container itself, its separately transcribed envelope table, its digest and byte-count checks against disk, and its byte-comparison re-run. The layout gate, called the best-bounded in the branch: sixteen named bounds, geometry implemented independently of the generator, a self-test against hand-computed cases, footprints taken from the inventory, a crashed check counted as failed, and its own limits stated rather than hidden. The level verification, which loads the saved map in a fresh editor and asserts the opened world before measuring, and refuses to save any world but the town. Process ownership in all three launchers, with a pre-launch baseline, owned-tree-only kills, leftovers failed as well as killed, and the report path deleted before launch so a stale file cannot be read as this run's result. The screenshot instrument, which hashes the exact bytes handed back by the engine and is then re-hashed and re-parsed from disk. The sprint A/B, same start, same duration, movement stopped between arms, differing only by the held key. And the discipline that nothing load-bearing is measured after direct state-setting: every placement row is marked as placement, not control evidence.

## Verification

All fifteen findings were repaired and re-verified. Each material repair was observed going red on the defect it names before being restored: the camera check at 31.6 cm separation and 368.1 cm view-to-camera with the camera activation deleted; the asset envelope checks on a `.glb` whose vertices were moved and whose declared bounds were left honest-looking; the layout clear-run bound on a layout where the probe would nearly walk into the well; and the triangle comparison against the real 5659-against-12168 numbers from the Nanite-on import that happened on this branch.

The orchestrator then ran the thirteen-step acceptance script on the integrated revision, green throughout, and inspected the captures at native resolution bound to their digests.

[Round 1](1_implementation.md) re-reviewed these repairs, confirmed fourteen of fifteen and found two further material defects introduced or missed by them.
