## Read-only diagnosis and minimal proposal for independent review

Exact failing source is frozen `native-proof.cpp:327-330`: wait the original owner handle, get its exit code, call `active(outer.job.h)` once, require zero. Original owner process and thread handles remain held until `outer.drain(true)` after scoring. In contrast, the crash path at lines 319-325 repeats successful accounting for up to 500 ms, still retaining those handles. The inner `Scope::drain` also repeats accounting, but explicitly terminates its job before the query. The experiment therefore does not presently separate handle-reference effects, termination mode, and accounting delay.

Exact counterexample: `events.tsv:2` is `SCORE_BEFORE_OUTER_RESCUE membership FAIL active=1 checkpoint=0`; lines 25-28 record inner `job active processes 0`, `pipe EOF observed separately`, and `scope drained handles closed 1`; lines 29-30 record joined outer rescue and 63-to-63 kernel handle balance. The run did not log the raw successful owner exit code or a diagnostic job process list. That missing observation cannot be reconstructed after cleanup.

Microsoft defines ActiveProcesses as current job associations and documents a decrement after process exit and release of all references; the latter wording follows the active-limit failure description, so the precise implication for these ordinary exits needs native discrimination rather than assertion. A process handle remains a valid object reference after termination. Job state queries require a successful API result. None of these contracts says that one immediate accounting query after a root wait is equivalent to completed drainage. [Accounting fields](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [process handles](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers), [job query](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject).

Proposed correction, **not implemented or executed**: after each successful original-owner wait, retain the wait and exit-code observation, log pre-release accounting and a read-only JobObjectBasicProcessIdList, close the now-completed original owner process/thread handles, and repeatedly obtain successful outer accounting observations before scoring and before any rescue. The outer job remains held throughout, as do any still-needed original rescue handles. Returned numeric IDs are diagnostic only; no OpenProcess or PID stop is introduced. Record post-release counts and elapsed time. Zero remains required; a failed query or a population that remains nonzero is failed/pending. This change must not make a timeout a clean receipt. The existing 28 arms, intended REDs and creation-window UNAVAILABLE stay fixed. Root must arrange independent review of this proposal before any modification or second scored native run.

For the negative controls, the independent reviewer should require a discriminating live-survivor observation rather than rely on the same questionable positive-count interpretation. That may be a joined fixture acknowledgement under outer containment or retained original fixture process handles transferred without copying the tested inner job; it requires review before implementation. The observer must never retain the inner job whose last-handle lifetime is under test.

Candidate jobs are unnamed, initially non-inherited, non-breakaway and KILL_ON_JOB_CLOSE; verified limit flags are checked. Job membership is supplied through PROC_THREAD_ATTRIBUTE_JOB_LIST in CreateProcessW, while explicit inherited handles carry only fixture synchronization/mapping and stdout, except the labeled job-handle leak mutation. Job attribute value and handle-list storage survive DeleteProcThreadAttributeList. Original process/thread handles remain until waits and cleanup. There is no OpenProcess, taskkill, numeric PID authority or browser SDK route. The only post-creation AssignProcessToJobObject path is the deliberately labeled negative. [Creation attribute lifetime and JOB_LIST contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

The extra held writer is native EOF counterevidence, not CDP framing proof. Runtime binding, thread-safe cancellation, helper/in-process integration, inherited fd3/4, transport callback timing, public SDK joins, pinned Chromium arguments and descendant-creation account remain unbuilt.
