# maps — repo-only rules

## Preserve existing markings before a scene rebuild

`npm run data:scene` checks `markings.mesh` and `markings-provenance.json` before geometry cleanup. It admits an absent pair as markings bootstrap, or a structurally valid and consistent pair in the existing published-only producer format. It refuses authored paint, unknown formats, missing partners and malformed or inconsistent records with the affected path and recovery requirements, leaving the existing scene bytes untouched. Restore a known pair when damaged; authored replacement needs a reviewed regeneration path. The preflight grants no new source authority and does not change `data:markings` or its provenance guard.

The bound is a read-only preflight before destructive work. Absence does not prove that no authored history existed; admitted builds are not transactional, and the check does not lock out concurrent external writers. Fixture checks and mutation evidence live in `test/scene-rebuild-preservation.test.ts` and `docs/learning/gate-proofs.md`. Clean-city rebuild and source-vintage acceptance remain separate.

## Stack

Vite, three.js and TypeScript, on Node 24 pinned in `.nvmrc`. Decided in the Shibuya plan (`docs/work/0_shibuya-1km/plan.md`) and built in Phase 0.

## Shibuya delivery ownership and autonomous work

For the approved Shibuya deliverable, the root orchestrator coordinates and delegates implementation to bounded workers, owns shared contracts and canonical status, and accepts the final integrated revision. Managed work continues autonomously in goal mode through the whole deliverable; the owner's 2026-09-08 instruction to continue until done overrides the default automatic-repair cap for this scope. Use each worker's scoped goal where the available tooling supports one; never overwrite another worker's or the root's goal.

The existing target in `src/world/frame.ts` is 3,000 animated pedestrians and 200 vehicles at 60 fps and 1920×1080. Keep that target distinct from measured performance. The scope remains the roughly 1 km Shibuya simulated world and its approved phases; no second location, broader product surface or publication is implied.

The owner's 2026-09-11 delivery instruction is to commit each meaningful step toward the current unit of work once that step is reviewed and verified. The integration owner lands accepted milestones on main rather than holding every change until the grand vision is complete. All five gates still precede a code commit, and visual work still requires native inspection and resolution of material review findings.

The owner's 2026-09-15 instruction is to commit early and commit often: commit as soon as there is a meaningful unit of verified change towards the deliverable, and treat that as a rule of this repository rather than a preference. A unit is small enough to review and self-contained enough to revert on its own. This is what the expensive gate used to make necessary: `npm run visual` took about three hours, so a session that waited for a perfect whole landed nothing. It costs about five minutes since the appearance lane moved to the GPU on 2026-09-17, so the reason to commit early is reviewability rather than the price of the gate — but the rule is unchanged, and so is the practice of committing each accepted unit rather than holding it for the next one. The queue is the plan's unit list.

Where a gate can be transferred between revisions, the transfer is a proof and not a memory. A code commit inherits an earlier revision's gate results only when all three of these hold, and the commit message states which revision they came from and the check that established them: the built bundle bytes are identical, `data/scene/**` is unchanged, and the changed paths are outside the bundle graph. The check is `npm run build` followed by `Get-FileHash dist/assets/*.js`, against the hash recorded for the revision the evidence belongs to. Anything else re-runs the gate. A commit that only adds a tooling file no build reads still re-runs the build to show that, because that is a one-second check rather than an assumption.

`npm run visual` owns port 4319 and, until 2026-09-17, most of the machine's CPU for about three hours. It now takes about five minutes end to end — measured 2026-09-17 at 283.2 s and 309.8 s on consecutive runs, the second on the committed tree — so the resource it still owns exclusively is the port. Two gate runs at once would still fight over the GPU and the preview port, so exactly one runs at a time; what changed is that a lane no longer has to be chosen around three hours of it.

The owner's 2026-09-08 appearance requirement is two 3D styles, Cartographic and Satellite, selected through a World style dropdown. Cartographic takes the clean default Apple Maps view as its visual reference and adds finer scene detail; Satellite improves the existing phototextured treatment. A registry supplies the dropdown options and leaves room for later styles. Styles share world geometry, the running simulation and the current camera. Switching styles must preserve the camera and agent progress, and acceptance covers both styles at street, block and aerial distances through the actual dropdown, including keyboard input.

## Anything that can run on the GPU does not run on the CPU

The owner's 2026-09-15 instruction, and it applies to work as well as to rendering. This machine has an RTX 4090 and the CPU is too slow to be the default for work the GPU can do.

The owner restated it on 2026-09-16 — "if you can use multi-core, don't just use single core. If you can use GPU, don't use CPU" — and that restatement removed the last exception in this repository. Until then the 44 appearance frames stayed on SwiftShader, on the argument that a pixel set captured on one renderer cannot inherit a review written on another, and the argument was paid for at about a fifty-fold tax: measured 2026-09-15, the same predicate at the same pose needed 12 frames and 200 ms on the 4090 against 58 frames and 134.6 s on SwiftShader. **That trade is over. `npm run visual` captures the 44 frames on the GPU**, in about five minutes end to end instead of three hours, and every lane in this repository now names the renderer it ran on.

What is genuinely lost is stated rather than glossed: the certified frames are no longer machine-independent. They are this adapter's pixels. The gate pays for that three ways, and none of them is a promise:

- **The certificate names the hardware.** `tools/visual/gpu-identity.ts` reads the adapter and driver version from the machine at `--begin` (`nvidia-smi` first, Windows' device record as the fallback) and the certificate carries them beside the browser's own `glRenderer` string. Frames drawn on another adapter, or on the same adapter under a different driver, are not comparable to these and the binding refuses them rather than letting the comparison be made silently.
- **Every check that existed still exists.** The 44 expected frames, fresh timestamps, the build-bytes binding, the `sceneTreeDigest` and `harnessTreeDigest` bindings, the three lifecycle records, the per-spec manifests with camera poses and SHA-256, and the certificate's own refusals are unchanged. Nothing was loosened to make the run fast.
- **Every review stays bound to the digest of the bytes it inspected.** That was already the rule for a native-resolution review, and it is what makes "this frame changed" a fact rather than an argument.

The measured pace, so the next session inherits numbers rather than the argument: the ten hero captures cost **4,438.2 s on the software lane** (per-capture gaps 107.4 s to 795.0 s) and **88–91 s on the hardware lane**, with per-capture gaps of 1.4–3.6 s and one 33.7 s page reload; the whole 46-capture lane is **2.4 minutes at `workers: 3` against 3.9 minutes at `workers: 1`**. Restricting hardware to iteration, or software to "just this once", is the tax this section exists to refuse.

The standing question for any new lane or instrument is still which renderer it is entitled to, and the answer is now the GPU unless the subject *is* the rasteriser. `tools/post-chain/` keeps a software arm because its question is what the post chain does on that renderer; `docs/learning/gate-proofs.md` keeps SwiftShader as a reproducible red baseline for the settle and lifecycle bounds.

## The work is a list, and the list is the orchestration

A goal is carried by an explicit task list, not by a running commentary. The list is written before the work starts, derived from the deliverable's own acceptance criteria and phase steps rather than invented from whatever is in front of the session, and it is what the coordinator reads to decide what to delegate next, what the team has room for, and what is stuck. Each item is one bounded unit with one owner, and it is marked done when its evidence exists rather than when its work stops.

Deriving it first is what stops the failure this rule was written after: three population lanes went at one blocker in sequence while the acceptance list was in nobody's hands, and the list never showed that the populated render, the style switch, the flythrough, the frame-time measurement and the independent review had no owner at all. A commentary cannot be checked for missing work; a list can. Keep it current, mark items as they land, and read it before each delegation so the queue and the team are chosen together.

## Map data, and what its licences oblige

Three sources, settled in Phase 1. Provenance, URLs and measured constants are in `docs/work/0_shibuya-1km/design.md`; the exact credit strings are in `src/world/sources.ts`.

**PLATEAU Shibuya-ku FY2025** supplies buildings, terrain, road surfaces and street furniture. PDL 1.0, with CC BY 4.0 expressly permitted. No share-alike, commercial use allowed. Copyright sits with the local authority, not with MLIT.

**OpenStreetMap** supplies the road, sidewalk and crossing topology. ODbL 1.0.

**GSI** elevation tiles are a cross-check on PLATEAU's terrain and nothing else is drawn from them. PDL 1.0, category 2, so attribution alone and no Survey Act application.

Three rules follow, and each of them is cheap now and expensive later.

**Both PLATEAU and GSI require two lines, not one.** A source credit, and a separate statement that the data was edited or processed. This project reprojects, clips, retextures and converts, so the second line is required and neither may be dropped for space.

**The OSM-derived network graph stays in files of its own.** The rendered scene is a Produced Work with no share-alike attached, but the Phase 6 lane, sidewalk and crossing graph is a Derivative Database, and publishing the app obliges offering recipients that graph or a description of how it was made — ODbL section 4.6. Fusing it into the PLATEAU geometry risks having to offer the whole thing. This is recorded as a constraint on plan item 23.

**Nothing fetched enters Git.** `data/` is ignored, holds about 620 MiB downloaded and 1.4 GiB unpacked, and is regenerable by `npm run data:fetch`. The repository holds the recipe and the checksums. The two files under `test/fixtures/` are the exception and were promoted deliberately: they are real cut-down bytes from GSI and PLATEAU, both under 256 KiB, and `test/fixtures/README.md` records where each came from and under what terms.

## Fetching data is a script, not a set of instructions

`npm run data:fetch`. It pins the PLATEAU archive by exact length and SHA-256, checks the length first so a truncated download says "N bytes short" rather than "hash mismatch", and re-downloads anything that fails. Overpass output cannot be hashed because OSM changes daily, so it is pinned by the `timestamp_osm_base` the script records in `data/provenance.json`.

The one operational trap worth repeating here: `overpass-api.de` answers HTTP 406 to any User-Agent containing a parenthesised comment, which is exactly the form OSM convention asks contact details be given in, and 406 is documented as meaning "rate limited". Use a bare token.

## The world frame is a contract, not a convention

Scene units are metres, Y is up, the world origin is the Shibuya Scramble Crossing, +X is east and +Z is south. It lives in `src/world/frame.ts` and every system that places anything reads it from there.

Nothing carries an EPSG:6677 coordinate into the browser. The origin subtraction happens where the data is loaded, so coordinates in the scene stay inside a kilometre of zero and a float32 vertex buffer still has centimetres of resolution left.

The box itself lives in `src/world/aoi.ts` and is stated once: bounds, centre, projected extent, the EPSG:6677 origin, the mesh codes, and the Overpass bbox. `frame.ts` takes the world origin from it, `tools/data/manifest.ts` builds the archive member list from its mesh codes, and `tools/data/overpass-query.ts` builds its query from the same bounds. Restating the box in a fourth place makes it a fourth box.

Two axis traps meet in this projection: CityGML's `posList` is latitude-first and EPSG:6677 is northing-first. Flip either and Shibuya renders perfectly and mirrored, and no frame review here would catch it. `test/aoi.test.ts` gates the whole chain against measured coordinates, and it has been made to go red.

## The visual harness drives the controls; it never sets state

`tools/visual/` synthesises pointer and wheel events on the canvas through Chromium's own input path. It may read `window.__mapsHarness`, which is frozen and has no setter. It may not assign `camera.position`, call `controls.setAzimuthalAngle`, or call the render function.

This is the fleet canon's rule, not a local preference, and `src/harness/bridge.ts` enforces it structurally rather than asking for it. Widen that bridge with another observation when a later phase needs one; never with a mutation.

## This repo pins its own preview port and checks app identity before it captures

Dev is 5319, preview is 4319, both `strictPort`, both bound to an explicit 127.0.0.1. The harness reads the page's `app-id` meta tag and refuses the run before the first screenshot if it is not this app's.

Why: every repo in this fleet takes Vite's 5173 and 4173 defaults, and several have a server up at any time, so "something answered on the port" is not "our app is running" anywhere in the fleet. During Phase 0 a sibling project's `vite preview` was found holding 4173, and the visual gate attached to that app and waited ten minutes for a bridge it was never going to publish. Separately, a preview left on the default host bound `[::1]` only and refused every connection to `127.0.0.1` while plainly running.

Three things stop it now: the ports above, `reuseExistingServer: false` in `playwright.config.ts`, and the `app-id` check. The third has been made to go red on purpose — see `docs/learning/gate-proofs.md`.

This rule fixes this repo's exposure only. Every other visual gate in the fleet has the same one, and whether that becomes a fleet rule is the owner's call, not this repo's.

## Gate artifacts live in `artifacts/`

That directory ignores itself. Each visual specification replaces only its own output directory: `visual/hero`, `visual/sweep/satellite` or `visual/sweep/cartographic`. Retained recovery evidence and sibling specifications are outside that cleanup scope. The wrapper requires 44 fresh native 1280×720 frames, checks their hashes and unchanged build bytes after the complete run, and writes `visual/complete.json`. The certificate also carries which renderer produced the frames, the three hardware lifecycle runs with their timings and their renderers, a digest of the scene data the preview server served and a digest of the harness the lane ran — the build bytes alone do not determine the pixels, because the same `dist/` draws a different city against a different `data/scene/`, and the same bytes drawn by different specs are not the same evidence. This verifies the evidence set exists; every frame still needs native inspection. Promoting a frame to a fixture or golden moves it out of there; it does not get un-ignored in place.

Evidence here belongs to a task and is deleted when that task closes. Once the conclusion is recorded in `docs/work/`, `docs/learning/` or `docs/devlog/`, the raw output goes with the task; only the files a tracked document names by path stay. A directory being the place a run happened is not a reason to keep it, and a second copy of a run is not a second observation.

A worktree under `artifacts/` junctions `data/` and `node_modules/` to the primary checkout instead of copying them. A copy of `data/` is 1,430 MB of bytes this repository already has and can rebuild; nine such copies were measured under `artifacts/` on 2026-09-15, 12.9 GB of the 53.6 GB total.

**A lane that runs any data-writing command must not have `data/` junctioned.** The junction is safe for reading and for gates, and it is what makes `npm run visual` work in a worktree, but it means `npm run data:scene`, `data:markings`, `data:network`, `data:setup`, `data:agents` and anything else that writes `data/` write into the primary checkout's served data — which is the scene a running capture is photographing and the payload every certificate digest folds. On 2026-09-17 a lane did exactly that on instruction from its coordinator: two `data:scene` runs rewrote the primary's scene (the second failing after `cleanSceneGeometry` had already deleted it), and a `data:markings` run re-derived `data/network/network.json` from the live extract and broke its Review 10 pin. A lane that needs to build data copies the tree into a real directory inside its worktree, or writes to an output path it owns, and says which it did. The coordinator writing such an assignment owns the mistake as much as the lane does.

**A lane that needs to install or reinstall dependencies must not have `node_modules/` junctioned.** `npm ci` and `npm install` delete and rewrite `node_modules`, so run in a worktree whose `node_modules` is a junction they empty the primary's dependency tree and break every other worktree in the session at once — a lane did exactly that on 2026-09-18 and the primary was found at zero top-level entries, with every junctioned worktree's gate failing until `npm ci` was re-run in the primary. Install in the primary, or give the worktree a real `node_modules` of its own. Read this together with the data rule above: the junction convention is for reading and for gates, never for anything that writes.

The served scene's digest **was** a build identity until 2026-09-18: `sceneTreeDigest` folds each served file's bytes and `data/scene/manifest.json` carried `"builtAt"`, so every `npm run data:scene` moved the digest with byte-identical geometry and a certificate's scene binding could never be re-derived after a rebuild. **That is fixed** — the timestamp has left the served payload, and two consecutive `data:scene` runs now return the same digest (`7f2bab4b…` over 117 files at the time of the change), so a rebuild re-derives the digest a certificate binds. What remains true is the pair of cautions below it: a rebuild still rewrites `data/scene` and therefore re-issues the certificate rather than silently inheriting it, and it re-derives `roads.mesh`, which must then agree with the `roadsSha256` embedded in the pinned `network.json` — whose own re-run needs live OSM and fails its Review 10 pin. `node tools/visual/verify-output.ts --end` is the instrument that says which happened, and the register carries the incident and the fix.

Junctions and symlinks are never followed, by a size measurement or by a delete. `Get-ChildItem -Recurse`, `Remove-Item -Recurse`, `rm -rf` and git's own recursive delete all follow a reparse point, so a measured total counts the primary checkout once per worktree and a delete reaches files outside `artifacts/`. Remove the junction itself with `rmdir` before deleting around it.

**Before any recursive delete of a directory that has ever contained a junction, enumerate the reparse points with an instrument that cannot report a partial answer as a complete one** — no `-ErrorAction SilentlyContinue`, no swallowed access errors, and print the count it found so the number can be compared against the junctions the lane was told to create (`data`, `node_modules`) plus any nested ones a lane may have added (a lane isolating part of the tree makes junctions inside `data/`, such as `data/scene` or `data/plateau`). Unlink every one with `rmdir`, then verify the primary's own directories still hold the file counts they held before, and only then delete. `Remove-Item -Recurse` and `git worktree remove --force` are forbidden on any directory that has ever contained a junction. This is the second instance of the same class in three days: on 2026-09-16 `git worktree remove --force` emptied the primary's `data/` and `node_modules/`, and on 2026-09-18 a coordinator's cleanup followed seven junctions an enumeration had missed with `-ErrorAction SilentlyContinue`, emptying `data/network`, `data/3dtiles`, `data/agents`, `data/decorations`, `data/gsi`, `data/osm` and `data/plateau` at once. Both are recorded in `docs/learning/defect-register.md`.

Whether a worktree may be removed is not the same question as whether its branch is merged, and the difference cost real evidence on 2026-09-16. A lane writes its evidence under `<worktree>/artifacts/`, which is ignored, so it appears in neither `git status` nor an ancestry check: six worktrees whose branches were all fully merged were removed, and with them went paint-review's frames, its ten 1:1 crops and its `analysis.json`, frame-budget's `interval.json`, `sweep.json` and two phase files, and render-state's eight arms, twelve frames and six records. Round 30's review cites those crops by path and digest and `plan.md` quotes those performance numbers, so both now rest on artifacts that do not exist; post-chain's and style-ui's evidence survived only because those two lanes happened to write into the parent directory instead. Enumerate the untracked files under a worktree — `artifacts/reclaim/preserve-worktrees.ps1` does exactly this — and look for a `<wt>/artifacts/` tree in particular, before removing it. Merged is a statement about commits, not about bytes.

The size is checked rather than assumed: `npm run artifacts:size` reports every top-level entry in real bytes with reparse points excluded and never counted, names each junction and each copied `data/` or `node_modules/`, and exits non-zero when a copied input tree passes 512 MB.

Uncommitted work is checked rather than assumed too, and the instrument is `git diff HEAD`, not `git status --porcelain`. In this checkout `core.autocrlf=true`, so a worktree whose files were written under a different line-ending setting keeps a stale stat cache: git reports the paths as modified, recomputes their content on comparison, and finds it byte-identical to HEAD. Measured by the reclamation pass on 2026-09-16 and recorded in `artifacts/reclaim/preserve-summary.csv`: over the 45 worktrees in its census, `git status --porcelain` named tracked changes in **32**, all **32** of those carried a non-empty `git diff HEAD` (every one of the 32 captured patches passes `git apply --check`, which an empty patch cannot), and **30** of them differed from `main` — the 139 files it named held **101** that differed. The clearest case is `artifacts/network/milestone-20260911`, which reported **78 modified files** with an empty `git diff HEAD` for every one, because its branch was merely behind main. Read from `status` alone, that worktree is the largest piece of unlanded work in the repository and it holds none. The trap is directional — it invents work rather than hiding it — so the harm is a preservation pass and a handoff report built on files that do not differ, which then competes for attention with the content that genuinely exists nowhere. The false positives are not reproducible on demand, because any later content comparison refreshes the cache: `artifacts/crowd-stacking/wt` reported `tools/agents/spacing-metrics.ts` modified with no diff behind it during that pass, and the same command returns nothing today. Record the count when the census runs rather than re-deriving it afterwards. Establish a worktree's dirty set with `git diff HEAD` and treat `status` as a hint to be confirmed.

The owner's 2026-09-15 instruction is to reclaim scratch whenever there is an opportunity, not only when a task ends: at the end of each step of a goal, and after a verification has finished, before the next step begins. Reclamation is therefore part of finishing a step rather than a chore deferred to the end of a deliverable, and it runs on the same boundary as the verification that step owed — which is also the moment the raw output stops having a reader, because the conclusion has just been written into `docs/work/`, `docs/learning/` or `docs/devlog/`. Running it at that boundary is what keeps the measurement honest: the first survey here found 53.6 GB, of which 28.4 GB was reclaimable.

## A citation that says a change landed names a commit reachable from `main`

A citation that says a change landed names a commit reachable from `main`. A rebase leaves a dangling copy of the same commit with the same subject and author time, so a citation to the pre-rebase object reads correctly to anyone who runs `git show` on it while sitting in no branch and being prunable. A citation to a revision that has not landed says so and names its branch; if the branch is gone, say the revision is unfindable by branch.

The measurement behind the rule, taken 2026-09-18 at `main` `4efaea6`: an audit of every hex token cited in `quality-register.md`, `plan.md`, `handoff.md`, `docs/learning/lessons.md`, `docs/learning/gate-proofs.md` and `docs/learning/defect-register.md` extracted 91 seven-hex tokens. Four of them do not resolve to a commit and are numeral fragments read as tokens — `7853982` and `1308997` are the app's own `azimuth` literals, `5160775` its `polar` and `5970698` a seed — so the population is 87 cited commits, of which **78 are reachable from `main` and 9 resolve but are unreachable**. Every one of the 9 sits in no branch.

Five of the nine are errors. `68a4775`, `d2babb8`, `ddb87ac` and `4e71f19` are cited as landed, in `quality-register.md` and `docs/learning/gate-proofs.md`, and each is a pre-rebase duplicate of a commit that is reachable from `main`: `c0d0f7c`, `f8c9e7c`, `e0fe4e8` and `c910dc8`. The match is established with `git patch-id --stable` and not by subject, which is the point of naming the instrument — on all four pairs the patch-ids are identical (`d3e2fec9…`, `9fccdc28…`, `5a7a4ec6…`, `61bc721f…`) while the subjects and author times are identical too, so subject alone would have confirmed the wrong object just as readily. The fifth, `adb9d4f`, is cited as the revision of branch `phase-b-terrain-cap`; its counterpart `0c76789` is that branch's head, on the branch and not yet on `main`, so what has to change there is the citation and not the commit.

The other four are deliberate references to revisions that have not landed, and they are right to say so: `plan.md`'s `7a9538c` (`worker/scramble`), `cd3cbd9` (`worker/vehicle-gate`) and `40ca6d3` (`worker/vehicle-gate-rebase`), and `docs/learning/gate-proofs.md`'s `d73ef9c`, the branch docs revision the six unit-gate runs were taken on, whose landed counterpart `a6ddb3c` is **not** the same patch — `git patch-id --stable` gives `836456ad…` against `1caf8d5a…`, and the landed commit is the larger one, so the pair cannot be substituted for each other. None of those four branch names resolves in this repository's branch list today, so each of those citations is one branch deletion away from needing the second half of this rule: the revision is unfindable by branch and findable only by its sha.

The corrections the five need land in a later record pass and are not made by this rule, so a reader should not expect the four files that carry them — `quality-register.md`, `docs/learning/gate-proofs.md`, `docs/devlog/summary.md` and `docs/devlog/detailed/2026-09-17_phase-b-appearance-batch.md` — to change with it.

## A tracked document is written with the line endings it already has

These documents are CRLF, `core.autocrlf=true` is set and the repository has no `.gitattributes`, so a tool that rewrites a tracked document with LF-only endings produces a whole-file diff that buries the line that changed: `git diff` reports every line removed and every line added, and the correction inside it is invisible. Measured on 2026-09-18: a correction to two lines of `plan.md` reported **469 insertions and 469 deletions**, and `git diff --ignore-cr-at-eol` reduced the same file to the two hunks that were real.

Write a tracked document with the endings it already has, and when a diff shows every line changed, suspect the endings before believing the content changed. `git diff --ignore-cr-at-eol` is the check that separates the two, and it is what established what actually changed here rather than an argument about which copy was current.

## The visual gate is two lanes, and each one names its renderer

The visual wrapper admits only the primary Git checkout root. Every CLI step (`--reset`, `--begin`, `--end`) checks Git's checkout identity before changing evidence and refuses a linked worktree or a subdirectory, naming the primary root and `npm run visual` as the next command. Integrate reviewed candidate changes into the primary before its final gate; ignored frames and `complete.json` then survive removal of the candidate worktree. This does not protect primary artifacts from a later explicit cleanup. The two style-return approach frames remain lane evidence outside the certified 44-frame set.

`npm run visual` clears the previous certificate, builds once, pins those build bytes, the scene data the preview server will serve, the harness that will drive the browser and the GPU the frames will be drawn on, runs the appearance lane, runs the lifecycle lane, then certifies the complete 44-frame set against both lanes' evidence. The chain is `node tools/visual/verify-output.ts --reset && npm run build && node tools/visual/verify-output.ts --begin && playwright test --config playwright.config.ts && playwright test --config playwright.lifecycle.config.ts --repeat-each=3 && node tools/visual/verify-output.ts --end`. The two lanes differ by question rather than by renderer: both draw on the GPU, and each asserts the renderer it got and names it in its records.

The appearance lane (`playwright.config.ts`, which runs `hero.spec.ts`, `style-picker.spec.ts` and `sweep.spec.ts`) captures the 44 frames on the hardware renderer, since the owner's 2026-09-16 instruction. It declares `MAPS_VISUAL_GPU=hardware` itself, so `orbit.ts` refuses a silent software fallback at the first frame, and both capture specifications call `pixelLaneRefusal` in `tools/visual/lane.ts` at their first frame as well, which refuses any renderer string that names a software rasteriser; the wrapper asserts it a third time over every manifest it certifies. Wrong renderer, two mutations, both exit 1 in about a minute, both messages in `docs/learning/gate-proofs.md`. The lane runs `workers: 3`, one per specification file, because the three files are independent and one worker per file is the whole of the concurrency available; measured 2026-09-17 over the same four tests on the same tree, `workers: 1` takes **238.9 s** and `workers: 3` takes **144 s** (1.66x), with the two sweeps serialised inside one file as the critical path. `--fully-parallel --workers=4` was measured too and takes **114.7 s** (2.08x); it is not the configuration that landed, because the certificate issued for this change is bound to the tree that measured 144 s, and landing the last 26% is a separate change with its own re-certification.

The lifecycle lane (`playwright.lifecycle.config.ts`, `lifecycle.spec.ts` only, repeated three times in the gate) runs on the hardware renderer with the same URL, preparation, viewport and 15-second navigation / 60-second replacement bounds. The spec records the unmasked `glRenderer` from the frozen harness before the expensive preparation and fails by name when that string names a software rasteriser, so the lane can neither fall back silently nor pass on a machine that only has SwiftShader. It also asserts two things the elapsed-time bounds cannot see: that the page reported no console error and no uncaught error (`tools/visual/page-errors.ts`), and that the outgoing document recorded its own `pagehide` cleanup as completed (`src/harness/teardown.ts`). The second exists because Chromium reports an exception thrown while a document is being torn down to nobody — measured 2026-09-16 with a positive control in `artifacts/gate-integrity/wt/probe/pagehide-visibility.mjs` — so a page whose disposer throws finishes *faster* and would pass a lane that only times the navigation. Each run writes a record under `visual/lifecycle/`, and the wrapper refuses to certify without three of them newer than the run it is certifying, each naming the hardware renderer, an empty page-error list and a completed teardown.

Why the lifecycle lane keeps its own config once the renderer argument is gone: measured 2026-09-15, under SwiftShader the fifteen-second bound is spent inside Chromium destroying the outgoing page's WebGL resources rather than in the application, whose own `pagehide` work finishes in 2.1-4.3 ms while the replacement document's first script does not run until about +27.87 s. That is a different question from "photograph the city", with its own preparation, bounds and records. The red baseline, the three attribution arms and their hashes are in `docs/learning/gate-proofs.md`; the user-visible version of the bound is in the defect register.

A machine with no usable GPU reports the gate unavailable: non-zero exit, no `complete.json`, and a message naming the missing prerequisite. It is never skipped and never a pass. Running the wrapper with no step flag is refused rather than re-certifying whatever run is on disk. `--reset` is the chain's first step, ahead of the build, so a build failure stops the chain with no `complete.json` on disk — a reader can never mistake a failed run for a successful one, and `test/visual-instrument.test.ts` checks the order of the chain in `package.json`. Re-measure the SwiftShader baseline when the scene changes materially, such as populated agents or larger atlases; it is now a red control rather than the lane's pace.

### Four iteration lanes write frames, and none of them is the appearance set

Three lanes capture the same specifications outside the gate: `frame-budget` (the frame interval at 1920x1080, its own config), `populated-iteration` (the population, which no frame of the reviewed set contains) and `flythrough-iteration` (a moving sequence, whose subject is what changes between adjacent frames). What keeps them out of the certificate is no longer the renderer — every lane is on the GPU now — but the run: the verdict is the one the gate's own chain opened and certified, with the build, the served scene, the harness and the GPU pinned at `--begin`.

A fourth joined them on 2026-09-18: **`flicker-iteration`** (`npm run visual:flicker`, `tools/flicker/`, port 4324, `artifacts/flicker/`) captures **consecutive rendered frames of a camera that is deliberately still moving**, to judge the dusk criterion's "no flicker or crawl over a moving sequence". It is the one lane that must not settle the camera before the shutter. Every other lane waits for the camera to stop, because a frame taken mid-glide is not reproducible run to run; this lane cannot wait for the same reason read backwards, and the pair it judges is what a settled camera cannot contain. `src/app.ts` feeds `cameraStill` into `post.setStill`, so TAA never accumulates while the camera moves, in any run: this lane judges the non-accumulating path, which is the only path a moving camera has. Its judge is the pure module `tools/flicker/judge.ts` with 13 cases in `test/flicker-judge.test.ts`, plus `test/flicker-step.test.ts` (5) and `test/flicker-shutter.test.ts` (3); its failure classes — a byte-identical pair from a moving camera, a stalled render counter, the crawl bar exceeded, and a pair the estimator could not model — have each been made to go red (`docs/learning/gate-proofs.md`). **The crawl class is qualified: it was reddened at the fixture's five-frame span and cannot fire at the span this lane achieves.** `tools/flicker/judge.ts:504-505` compares `allowed = crawlFractionPerFrame * Math.max(1, pair.frameGap)` against `crawl = unexplainedFraction / Math.max(1, pair.frameGap)` (`:602`), so the predicate is exactly `unexplainedFraction > 0.005 * frameGap^2` - quadratic in the span. It needs more than the whole frame once the span passes `sqrt(1/0.005) = 14.14` rendered frames, and this lane's measured spans are 20.5-23 (`artifacts/flicker/capture/manifest-{orbit,ascent}.json`), where it would demand 210-265% of the frame. Crawl is therefore **measured** at the criterion's regime and **not gated** there, and a `no failures` line from this lane must not be read as the crawl class having been enforced. Its two runs and their bounds are in `artifacts/flicker/RUN-02-REPORT.md`.

**The flicker lane's cadence is the screenshot's, and its record says so.** A native-resolution screenshot costs about 300–400 ms on this renderer, so 29 to 34 frames are drawn across the **pair's two shutters** and the closest two stills it can take are 20.5 to 23 rendered frames apart, midpoint to midpoint — not the one to three rendered frames the criterion names. **The pair sum was reported as a per-still figure in five places, including `RUN-02-REPORT.md` and two docstrings; the measured per-shutter spans are 16–17 frames on `orbit` and 14–18 on `ascent`, the same regime as RUN-01's 16–18, so the claim that the shutter span grew is backwards** (`artifacts/flicker/capture/manifest-{orbit,ascent}.json`, `frameCountAfter - frameCountBefore`). What grew is the idle-plus-two-shutters cycle the midpoint-to-midpoint span legitimately measures. The lane reads the frame counter and the pose on **both** sides of every shot, records the **midpoint** as the frame's pose, and measures a pair's span midpoint to midpoint, so the recorded motion and the span it is divided by describe the same window; the achieved span, the shutter span and the idle time between shutters are each in the record per pair. `judgeFlicker` refuses a pair spanning more than `FLICKER_CADENCE.maxPairGapFrames` (26) frames rather than implying a cadence the instrument does not have, and that bound is deliberately tight — measured 20.5–23 against it, so a slower scene trips it rather than being absorbed. Its crawl bar (`CRAWL_FRACTION_PER_FRAME`, 0.005 per rendered frame) was set from two synthetic controls — a pure shift measures **5.934e-5 to 1.563e-3** and collapsed detail **5.154e-2 to 5.326e-2** when round 35 re-ran the shipping judge over the shipped fixtures, a wider separation than the 1.2e-4 to 1.6e-3 and 3.7e-2 to 5.2e-2 this line carried, so no verdict moves but those were remembered numbers — and the first two real runs measured **9.995e-4 to 1.351e-3 per frame** against it, on pairs the estimator can model. It **remains provisional and those runs do not calibrate it**: the synthetic null moves the picture ~3 px a frame against the lane's measured ~0.7, so the control and the record are not the same regime, and a real-scene null at the real motion scale does not exist in this lane. The bar's per-frame form is a known flaw, and it is worse than "looser": the predicate is `unexplainedFraction > 0.005 * frameGap^2`, so the bound on the fraction of the frame tolerated is **quadratic** in the span. `allowed` is 0.005 times the span, but it is compared against `crawl`, which is the unexplained fraction already divided by the span, so at a 23-frame span the judge will tolerate 2.645 of the frame - more than all of it - and past `sqrt(1/0.005) = 14.14` rendered frames the class can never fire. The report's headline "worst pair 1.351e-3, 3.7x under the shipped 0.005" therefore compares a measurement against a constant the judge never applies to a pair: at a 22.5-frame span the allowance is 0.1125. The fix direction is to bound the pair's `unexplainedFraction` directly. **`ascent` emits no wheel event at all.** `tools/flicker/motion.ts:225-229` sends `mouse.wheel(0, -60)` only when `wheelAccumulator >= 16`, and the run makes 12 gestures (`manifest-ascent.json` `motion.gestures` is 12, `orbit` 11), so `distanceM` is constant across all twelve frames of the ascent run - 44.99999965195447 to 44.99999965195452, five distinct floats inside 5e-14 m - and the criterion's "or an ascent" pose is not exercised. `MotionConfig.wheelTicksPerSecond` (`motion.ts:106`) is dead config, the same class as the register's `spacingQueryRadiusM` entry. **And the fine pass's window is 23 px, not the 41 the comment, the report, the devlog and two register rows claim:** `judge.ts:737` uses `Math.floor(Math.min(width, height) / COARSE_CELLS) + 1`, which is 23 at 1280x720 and 4 on the 192x108 unit frame, where 41 and 7 are the `Math.max` values. The 23 px window is below the coarse grid's own 40x22 px cell while `atBoundary` tests the 24 px radius (`:748`), so a fine pass clipped by its own window is reported as a confident shift rather than as unmodelable; every shift in these runs is 0-2 px, so it is a bound to state rather than a live failure.

**An instrument that cannot model a pair must say so, not return zero.** A camera translation is the judge's model, so the estimator's search radius is a real bound on what the lane can judge; a pair whose best shift lands on that radius now fails **by name** as unmodelable, because a failed search and a still picture both answer `0,0` and they are not the same statement. The lesson generalises past this lane: a sentinel with no channel to say it is a sentinel is read as a measurement, and RUN-01 published `changed = 1.0000` and a clean verdict over nine pairs the estimator could not follow. When a lane's own predicate is what failed, the record has to be able to say that.

- **Each writes under its own ignored directory.** `tools/visual/lane.ts` maps each lane name to a root and the specs resolve their output paths through `laneDir()`. An unrecognised value throws instead of defaulting to the verdict directory.
- **Each names the renderer.** The iteration lanes require `MAPS_VISUAL_GPU=hardware`, which is also the switch `orbit.ts` uses to refuse a silent software fallback; the `glRenderer` string is recorded in the console output and in every manifest.
- **None can certify.** `tools/visual/verify-output.ts` calls `assertCertifiable()` before writing anything and refuses every lane but `verdict` by name, each in that lane's own terms. Only the verdict lane produces `complete.json`, because the certificate binds the run's own build, served scene, harness and GPU, which only the gate's chain pins.

`playwright.hardware.config.ts` and `npm run visual:hardware` are gone: they existed to iterate on the GPU while the verdict stayed on the CPU, and once the appearance set moved they were a second lane claiming to be the appearance gate. Their per-test budget reasoning survives in `tools/visual/budget.ts`, whose ceilings are the software pace kept as backstops — measured 2026-09-17, the hardware lane runs the whole 46-capture set in about a minute and a half of ledger time.

## A shared tool's names are not evidence, and a fan-out needs one scratch directory per lane

Two rules, each from a named incident rather than a preference.

**`tools/inspect/crops.ts`'s region names are screen geometry and carry no material claim at any pose.** The names - `near-pavement`, `left-ground`, `right-ground`, `centre-crossing`, `upper-signage-sky`, `right-ui` - describe rectangles of the 1280x720 capture frame (`tools/inspect/crops.ts:119-179`), and what falls inside one depends entirely on the camera. At a 63 m camera pitched 16.7 degrees down over the cartographic block the bottom band is **roofscape at five of the six azimuths**, so `near-pavement`, `left-ground` and `right-ground` name roofs (`artifacts/inspection-final2/REPORT-cartographic-block.md:164`); at the hero crossing pose the cell a prior report called road is **pavement**, and the asphalt there is the mid-frame band inside `centre-crossing` (`artifacts/inspection-final2/REPORT-hero.md:145-147`); the noon rect the task called the crossing's "asphalt band" contains no road surface at all (`artifacts/inspection-final/REPORT-hero.md:133`); and the same crop name is asphalt at `plaza-az000` and pavement at `plaza-az060` (`artifacts/inspection-final2/REPORT-satellite-plaza.md:50,53`). A quoted phrase attributed to a report turned out to be the crop tool's own region note for `near-pavement` (`tools/inspect/crops.ts:166-168`), which every crop manifest copies; the pre-batch satellite-block lane's az060 `right-ground` box called "plain asphalt left of the zebra bars" is at 4x a smooth dark green-grey plane - the lowest cross-preset correlation of any road box (r = 0.430) and the lowest 5x5 local-sd median (0.63), so the "weakest road in the subset" figure that box produced measures a plane and not asphalt - and its az300 "pale street surface in the canyon" box is at 5x a banded facade with a window grid (`artifacts/inspection-final2/REPORT-satellite-block.md:169-170`). **The rule:** a lane classifies a surface itself, from the pixels, and says what it based the classification on - the working example is `artifacts/inspection-final2/REPORT-satellite-plaza.md:47` ("Material labels are taken from the pixels, and cross-checked against the adjudication's table"). A crop-tool label is never the basis. **Prescribed, not made here:** the tool's own docstring should say so; that is a change under `tools/`, so it needs the five gates.

**A fan-out whose lanes share one scratch directory collides.** Re-inspecting one certificate, two lanes wrote into `artifacts/inspection-final2/` at the same time: one overwrote the other's `project.mjs` with its own projection script, unrecoverably, and the two lanes' instruments then sat in that one directory under names that could clash. The lane that caused it discloses the overwrite and the prefixes it adopted afterwards to avoid more of them (`artifacts/inspection-final2/REPORT-hero.md:166`). **The rule:** a fan-out gives each lane its own subdirectory under the shared output root, and a lane writes only inside it. The same discipline is already mechanical where it can be: `tools/inspect/crops.ts:668-677` refuses by name to write crops into a directory that already holds a different frame rather than mixing two frames in one review. The incident is in `docs/learning/defect-register.md`.

## The scene is built offline and served from `data/`, not bundled

`npm run data:scene` reads `data/plateau/` and `data/3dtiles/` and writes `data/scene/` — the terrain mesh, the road mesh, a clipped tileset and 67 placed building tiles, about 148 MB. `tools/vite/serve-scene-data.ts` serves that at `/scene/`, and three.js's Draco decoder out of `node_modules` at `/draco/`, in the dev server and in `vite preview` alike.

The alternative was Vite's `public/`, which copies everything into `dist/` on every build — and `npm run visual` builds before every run. The cost of this choice, stated here so it is not rediscovered: **`dist/` is not self-contained.** Serving it from anywhere other than `vite preview` means serving those two directories too. The app names the missing file rather than drawing an empty city.

Everything under `data/scene/` is in the world frame already: metres, Y up, origin at the crossing. No latitude, no EPSG:6677 northing and no ECEF position reaches the browser.

## 3D Tiles: two rotations, and getting either wrong renders

MLIT's `.b3dm` tiles state their position as a `CESIUM_RTC` centre in ECEF metres, and their vertices are **Y-up in the glTF convention** over data that is **Z-up in ECEF**. Nothing in the file says so. Placing a tile therefore needs the turn as well as the translation, and the two ways to get it wrong look the same from the inside:

- **Turn missing.** Every building lands a median of 68 m from where its own batch table puts it, up to 122 m, and the city renders lying on its side over the correct street pattern.
- **Turn applied twice.** `3d-tiles-renderer` applies its own from `asset.gltfUpAxis`, which defaults to `"y"`. A pipeline that has already folded the turn in must declare `gltfUpAxis: "z"` — `tools/tiles/tileset.ts` does.

`test/placement.test.ts` gates the transform and `npm run data:scene` reconciles every building's decoded geometry against its batch table, refusing at 2 m of horizontal residual. Neither can see the second application; the visual gate's drawn-geometry bounds are what caught that.

## Texture memory is this scene's binding constraint

The 67 building tiles carry 551.9 megapixels — **2,943 MB decoded to RGBA with mipmaps**. The tile cache counts decoded bytes, not downloaded ones, and a cache too small to hold a leaf tile does not degrade: a `REPLACE` parent waits for all its children, so the traversal deadlocks at the root and the app draws seventeen decimated buildings while reporting itself loaded and idle.

Letting the hierarchy stop higher up is not an answer either, because PLATEAU's coarse levels are decimated to **255 buildings of 1,740** at depth 4. The fixed geographic policy uses 1024 pixels generally, 2048 for tile bounds within 160 m of the crossing, and native 4096 for the single final-detail leaf containing the observed frontage at world `(-38.58,21.58)`. `npm run data:textures:verify` requires that frontage policy to select exactly one leaf and one atlas; current source resolves to `data518.b3dm`. Runtime selection uses geographic metadata rather than that filename.

The full-source audit selects 17 priority tiles including the native leaf: 561,075,583 estimated decoded texture bytes with mipmaps plus 73,324,734 geometry and facade attribute bytes. The native leaf adds 67,108,864 bytes over the otherwise identical 2048 policy. A frozen 1280×720 controls-driven comparison recovered TSUTAYA lettering and glazing detail; it did not materially improve the distant approach view. These are allocation estimates and scoped visual evidence, not whole-process GPU measurements or proof of the population performance target. The tile cache uses a 640 MiB floor and 768 MiB ceiling, with each tile's byte estimate rounded upward to an integer because fractional residue can prevent the upstream LRU from terminating disposal.

Both styles reuse the same cached capped atlases. Source ImageBitmaps are released after processing, so this is fixed geographic priority and does not promise camera-dependent resolution upgrades. `src/scene/texture-budget.ts` holds the policy; actual processed dimensions and per-view ray-hit atlas dimensions are observed through the read-only harness.

## Traffic hardware is separately authored presentation

OSM traffic-control coordinates retain their logical meaning in the network; they do not establish surveyed pole or head positions. `npm run data:hardware` writes separate `/scene/control-hardware.json` records after network, final pavement and vehicle assets exist. Every source control is placed with disclosed local support/clearance evidence or explicitly unplaced. Runtime rejects missing, malformed or stale geometry/network inputs with the rebuild command. Unplaced hardware must not delete its source control or change signal authority.

The current hardware proof uses the actual generated fleet manifest at displayed scale 1. A new fleet or larger scale must regenerate and recheck hardware clearance; city-only startup does not load the fleet solely to perform this future assertion. Discrete supported pose checks do not establish continuous traffic collision safety or accepted whole-city pavement contact.

## PLATEAU road polygons below LOD3 are flat at sea level, and the edge is the worst part

`tran` LOD1 and LOD2 are flat at z = 0 — every vertex, measured — so they must be draped onto the terrain. What `design.md` did not warn about is what happens to a road ring that reaches past the terrain: there is nothing to drape it onto, it keeps its own height of zero, and a sheet of asphalt appears fifteen metres under the valley extending past the edge of the ground. `tools/scene/build-roads.ts` drops any ring with a vertex off the terrain, and `npm run data:scene` refuses a road mesh whose lowest vertex is more than 5 m below the lowest ground.

## Physical paint is a bounded presentation overlay

Crossing and tactile paint reads source path elevation to select nearby road/pavement support; it must not choose an unrelated highest X/Z layer or fall back blindly to terrain. The current finite checks and explicitly omitted parts are documented in `docs/reference/pavement-recipe.md`. The maximum 10 mm opposed-edge seam allowance belongs only to paint presentation; it does not alter source meshes or authorize vehicle/pedestrian contact. ## Software visual verification budgets

The first final SwiftShader attempt measured 6m20 to the first hero capture, 4m11 to the next, and 2m52, 2m52 and 3m17 between plaza sweep captures. These are costs of the 1280×720 software verification lane, not measurements against the separate 1080p hardware performance target. Lifecycle reserves thirty minutes total setup, three minutes initial refinement and eight minutes per pose while retaining its fifteen-second navigation and sixty-second loaded-page checks. Playwright stops after its first failed test and preserves that failure's trace.

**Every per-test budget is derived from the captures that spec makes, and the numbers live in `tools/visual/budget.ts` rather than in a comment.** The round numbers these replace were the measurement rather than a budget: the hero block took 49.3 minutes on one 2026-09-15 run and 50.4 minutes on the next (first frame 20:28:02, last 21:18:26), and the 60-minute `test.setTimeout` fired eight seconds before the last of those ten frames landed — a complete capture set failed by a clock. Same defect class as the settle budget, same answer: `setup + captures x per-capture allowance + margin`, with the allowance set from the worst pace that spec has shown (hero 9 min per capture against a 5m32 worst interval; sweep 7 min against 3m17), and `captureLedger()` in `tools/visual/progress.ts` writing each capture to `captures.json` as it lands so a run cut off by any ceiling names the capture it died in.

Measured values: hero 105 minutes, each sweep style 141 minutes, lifecycle 46 minutes. The owned full-run wrapper's deadline is **38,700 seconds**, derived as that 525-minute sum plus two hours for the build, the preview server and report writing. The per-test budgets add up to less than the wrapper by 120 minutes, which is what makes the wrapper a backstop rather than the thing that fails a run whose own ceilings were never reached. The 14,400-second deadline this replaces was shorter than `hero` plus a single sweep on the observed pace, and the per-test budgets declared beside it summed to 27,360 seconds — a run that could not finish inside the time it was given. `test/visual-budget.test.ts` checks all of that arithmetic in both directions. No retry or backend substitution is implied.

**The settle wait is bounded in frames, not in wall-clock time alone** (`SETTLE_BUDGET` in `tools/visual/orbit.ts`), because the predicate is frame-counted and only the price of a frame differs between renderers. Measured 2026-09-16: the same predicate, pose and build need 12 frames / 200 ms on the RTX 4090 over D3D11 and 58 frames / 134.6 s on SwiftShader, whose frame interval ranged 16.6 ms to 6,150 ms within one run — a per-frame cost moving 370x, which no fixed deadline can track. Three bounds apply, and a failure names the one it hit:

- **320 frames advanced**, the real budget. Hardware needs 12 frames for a correction and 76 for the longest measured `orbitTo` correction, so this is about 4x the worst observed need and more than 4x the 71 frames the failing run reached.
- **30 minutes of wall clock**, a loose backstop for frames that do advance but so slowly that waiting is pointless. It is 6x the 300,000 ms deadline it replaces, so that under any frame cost this lane has shown, the frame budget is what fires.
- **A stale-frame bound of 15 seconds, or 8x the longest gap measured between two advances, whichever is larger.** The multiple is set from the measured spread (max/median interval 2.5x, largest observed gap 6,150 ms). The floor has to stay below a renderer's own real gap: a gap longer than the floor can never complete, because the detector fires first, which is what turns an adaptive rule back into the constant it replaced.

The failure messages state which of the two happened, in as many words: *the renderer stopped advancing frames* is a stall, and *frames advanced but the predicate was not satisfied inside the budget* is a budget failure under load. The three cases — budget failure, stall, and satisfied — are unit cases in `test/camera-settling.test.ts`, each made to go red by mutation in `artifacts/gate-speed/REPORT.md`.

The camera observer reads frame count, document epoch and full pose in one browser task. Only fresh rendered frames count toward quiet intervals. Ordinary capture settling uses angular/relative movement; the stricter 80 micrometre world-path baseline applies only before dropdown preservation comparisons. The pinned no-input OrbitControls damping is enabled at 0.08; three qualifying fresh intervals and at least twelve advanced frames leave a bounded sub-millimetre residual in that path. The independent five-millimetre post-switch assertions stay unchanged. These polling checks do not cancel an unresolved browser RPC; outer Playwright test/stage and owned-runner timeouts bound that case. CPU fixtures do not replace the actual software dropdown and native image gate.

## Moving dusk capture and the unresolved comparison model

The Q3 component uses twelve adjacent native canvas copies in RAF, with exact same-task frame/pose/post binding, actual sustained pointer and released-pointer wheel input, and PNG encoding after each burst. `npm run visual:flicker` remains an iteration command and produces no certificate. Every copy must be nonblank, every pair adjacent and moving, and every post observation non-accumulating. A gap or invalid copy is refused, not skipped.

The unchanged 0.005 provisional bound applies directly to the unexplained-feature fraction over shared complete 3x3 neighbourhoods. Its integer translation model also rejects legitimate fractional, rotated and depth-varying synthetic motion. Every report therefore declares `sceneVerdict: not-established`: a high residual is unresolved motion-model error, not proof of a renderer defect, and a low residual is only a bounded observation. Q3 scene acceptance remains open until an independently reviewed motion model separates legitimate motion from injected defects. The [component record](../work/0_shibuya-1km/snapshots/q3-motion-capture-review43.md) preserves the superseded capture failures and final frame hashes.
