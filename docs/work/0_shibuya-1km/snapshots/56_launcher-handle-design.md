## Source-backed facts and their limits

Windows keeps a process handle valid after exit until the handle is closed. An independently held duplicate references the same kernel object. The PID remains tied to that object while it exists; the no-reuse claim uses Microsoft's explicit process-ID explanation, not only a generic handle lifetime analogy. [Process handles](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers), [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle), [PID reuse explanation](https://devblogs.microsoft.com/oldnewthing/20110107-00/?p=11803). The last article was available in the search result; direct page retrieval returned 403. These are API/source premises, not a native experiment in this pass.

`TerminateProcess(hProcess)` addresses the retained object, requires termination rights, and starts asynchronous termination. Waiting on that same handle is needed to establish exit. An already exited process can make termination return access denied; the wait result must distinguish that from an unobserved refusal. Root termination does not terminate its children. A retained HANDLE does not keep a process running and does not confer its identity on descendants. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [Process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

## Smallest useful lease API and the unsolved membership boundary

A native process lease needs opaque owner/generation identity, not a public integer HANDLE that can be closed and reused by arbitrary callers. Its minimum operations are `retainOriginalBeforeRelease`, `requestTermination`, `waitForExit`, `readCreationIdentity`, and idempotent `releaseAfterAllConsumers`. Internally it owns a noninheritable HANDLE with SYNCHRONIZE, PROCESS_TERMINATE and required query rights. Termination and observation use that handle. Failed duplication/open/wait/close is an explicit unverified state, never an empty inventory. Disposal cannot release a lease while an asynchronous waiter is using it.

The strongest acquisition boundary is direct duplication of the original `CreateProcess` HANDLE before its owner can release it. This requires a native spawn boundary or a supported native hook; BrowserServer's public API does not supply it. A potentially smaller root-only route is a synchronous native `OpenProcess` call from the original ChildProcess's `spawn` listener, attached before launch through Node's documented diagnostics channel. The source publishes the ChildProcess in its constructor; successful spawn schedules `onSpawnNT`; the documented spawn event precedes the other events. An immediate native call at that boundary could take another reference while Node's original reference still exists. This is an inference from exact source and API ordering, not a validated implementation. It is materially different from an asynchronous inventory followed by OpenProcess, which has no continuity proof. [Node spawn ordering](https://nodejs.org/download/release/v24.12.0/docs/api/child_process.html#event-spawn), [Node process diagnostics](https://nodejs.org/download/release/v24.12.0/docs/api/diagnostics_channel.html#event-child_process).

That root route still needs proof of exact launch-scope attribution, hook installation before every relevant constructor, synchronous native retention without yielding or reentrancy, rights and retention-failure cleanup, and an acquisition ledger that exists before calling launchServer. The ledger must register before checking cancellation and must join each started or late acquisition. A failed launch that never returns BrowserServer still belongs to that ledger. The native object may already be signaled at first inventory, yet the lease must remain until every SDK force path, including its internal fallback and process-exit handler, is unreachable and joined. Acquiring only in the successful launchServer continuation cannot cover failure before that return.

Most critically, Chromium's own children are not Node ChildProcess constructions in the launcher. The root hook therefore cannot retain them. Holding a root plus all handles collected from snapshots protects only that known subset. The SDK's `/T` does not supply a reviewed handle-level membership/termination contract for descendants. This study did not inspect taskkill's implementation and does not assert a new native descendant PID-reuse exploit. It cannot use taskkill to turn partial membership evidence into complete ownership proof.

## Restricted impossibility certificate

The claim is limited to mechanisms whose only ancestry information is a finite sequence of live-process rows (PID, parent PID, creation date, name/path) and retained handles for identities already admitted from those rows. Assume descendants may start and exit between snapshots, and no atomic birth stream, creation barrier or complete membership authority exists.

The JSON case `missing-intermediate-produces-indistinguishable-live-rows` gives two histories. At the first observation, owned root 222 exists. Between observations, process 333 is created and exits, having created live leaf 444. In history A, 333 descended from owned root 222; in history B it descended from unrelated process 999. Root 222 is exited at the final observation but its handle remains retained in both histories. Every observed row and retained-root wait result is identical, including leaf 444's creation time and historical parent PID 333. Only the unobserved edge differs. The leaf can use the same executable and profile-like command text in either history, so those fields add no authority.

A method receiving those observations makes the same decision in both histories. Killing 444 violates no-foreign-kill in B; leaving it violates no-orphan in A; waiting forever cannot establish successful finite cleanup in A if it stays live. Reporting unverified is honest but does not satisfy acceptance. Repeating finite snapshots cannot recover the vanished edge. The simpler last-inventory case also shows a new child may survive exact handle termination of every previously known process.

This rejects root/known handles plus finite snapshots as a complete solution under the stated assumptions. It does not reject native handles as a primitive, all uses of BrowserServer, or every possible process-supervision strategy. The argument and model need independent scrutiny before root records a strategy-level decision.

## An expansion that changes the missing assumption

Windows `DEBUG_PROCESS` can provide creation events before user-mode execution, with a process handle in each event. A debugger duplicates the handle before continuing the exit event and can wait on the duplicate. This is a concrete example of stronger information than snapshots, so a whole retained-handle strategy is not disproved. It is not a completed design here: Windows documents that a new DEBUG_PROCESS launch starts a new debugging chain; applicable rights, Chromium launch/sandbox behavior, external brokers, debugger lifetime, and all event/handle drainage require separate proof. No debug process was created. [Debugging events](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-events), [Creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [WaitForDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent).

A helper is not an answer by itself. Any helper would need to expose that complete acquisition authority and joined exit/handle receipts, remain owned through communication failure, and have its own process lifetime accounted for. Relocating the same snapshot logic behind a helper preserves the counterexample.
