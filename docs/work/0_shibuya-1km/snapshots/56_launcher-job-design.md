# Windows job ownership study

Owner: launcher_job_design. Base revision: `82ee91772f9533ab3e8661f73af2eb4eb1e2bd3c`. Scope: one independent design pass, 2026-09-19. No launcher implementation or native admission is claimed.

## Result and decision for root

The smallest credible job-family design has two inseparable parts: create Chromium inside a private non-breakaway Windows job before its initial thread can run, and attach Playwright through an owned pipe transport so Playwright never owns a numeric-PID termination route for that Chromium. A job around unchanged BrowserServer is rejected: job membership restricts which processes the job terminates, not which processes its members can ask `taskkill` to terminate.

For the current Windows host, prefer job assignment during `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_JOB_LIST`, not a post-creation assignment fallback. Microsoft explicitly identifies owner death between suspended creation and assignment as an orphan window and documents assignment during process creation as its remedy. This is a supported mechanism, not native verification of a new launcher. [Microsoft explanation](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812), [creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

The remaining native piece is specific and unbuilt: one Windows ownership boundary that creates the job and process together, wires Chromium's inherited CDP pipes, retains original handles through failed setup, terminates only through those handles or its job, and produces an observed drainage receipt. The installed SDK's public custom-transport attach API supplies a concrete way to avoid its PID launcher without patching dependency code. Its native compatibility, full late-acquisition behavior and capture fidelity must still be proved. This study does not call that integration routine.

## Smallest proposed ownership API

An in-process Windows native boundary avoids introducing another helper process whose ownership would itself need proving. This is a proposed interface, not a new dependency or an implemented addon. A native helper executable could implement the same contract, but would need additional inherited control-pipe, helper-drain and owner-death obligations; it is larger than the boundary assessed here.

```ts
type OwnedBrowserScope = {
  ready: Promise<ConnectOverCDPTransport>;
  requestStop(reason: string): void;
  drained: Promise<OwnedBrowserDrain>;
};
// Registers ownership before scheduling any native creation.
beginOwnedBrowser(spec: FrozenBrowserLaunch): OwnedBrowserScope;
```

The opaque scope owns one unnamed job, original process/thread handles, its pipes and I/O operations. It exposes no PID-based stop or PID-to-handle reopen function. `ready` may reject or arrive after cancellation; both remain registered and joined. `requestStop` is idempotent, latches cancellation before any later acquisition, and returns no completion claim. `drained` is the separate authority receipt for observed job zero, original root wait, closed native handles/pipes, settled I/O and retained failures. It cannot resolve successfully from a timer, root exit, SDK disconnect, a known PID subset, or a job notification alone.

The caller owns profile and artifacts directories from their creation, retains them across failed and late launch, and removes them only after native drainage and relevant SDK/context/page closure have settled. A failed removal remains failed even if a subsequent retry removes the directory. Existing server listen, HTTP connection closure and build drainage remain separate joined acquisitions. A browser-job receipt cannot certify Vite/build workers; their actual child creation and disposal must remain covered by the whole-launcher acceptance evidence.

## Creation contract and failure rescue

1. Validate the supported Windows version and native module before starting work. Create an unnamed non-inheritable job; set `KILL_ON_JOB_CLOSE`, with both breakaway flags absent, and verify the applied limits. Keep job assignment, query and terminate rights privately. No child receives the job handle. No unrelated process is assigned to this job. [Job limit flags](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).
2. Prepare the dedicated pipes and `STARTUPINFOEXW`. The explicit handle list contains only intended child pipe ends; it excludes job, parent and controller handles. Create the exact executable without a shell using `EXTENDED_STARTUPINFO_PRESENT | CREATE_SUSPENDED`, `PROC_THREAD_ATTRIBUTE_JOB_LIST` containing the private job, and a native hidden-window policy. The job-list value and attribute storage remain alive until creation finishes. The local handle transfer, CRT fd 3/4 mapping and pipe encoding must be reviewed against the pinned Node/libuv stdio implementation and Playwright pipe framing. No pipe implementation is claimed here. [Creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [Node/libuv Windows stdio](https://raw.githubusercontent.com/nodejs/node/v24.12.0/deps/uv/src/win/process-stdio.c).
3. Retain the original `PROCESS_INFORMATION` handles immediately. Before resume, successfully query membership in the exact job and cancellation state. Failure or cancellation takes the owned abort path. Only resume once with an expected prior suspension count of one; any unexpected result is a setup failure. `CREATE_SUSPENDED` prevents the initial thread from running before resume; it does not mean closing its handles terminates it. [Process creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread).
4. For any successfully created process whose setup fails, retain the original process handle, request termination through that handle or the verified job, and wait for actual root termination before releasing it. `TerminateProcess` returning success is asynchronous. If termination reports access denied, check whether the original handle is already signaled; do not reinterpret every access-denied response as successful cleanup. Retain the primary creation/membership/resume error and every cleanup error. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

The alternative explicit sequence `CreateProcess(SUSPENDED) -> AssignProcessToJobObject -> ResumeThread` closes the child-execution race when every step is checked. If assignment fails, the child is not presumed terminated: some documented limit failures terminate it, other failures merely return an error. The original handle is the rescue authority. A control must cover nonterminating assignment refusal and failed cleanup, not only the limit-exceeded branch. This independently supports the failure case requested from old LEGO memory without treating that old run as maps evidence. [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject).

That explicit post-creation route still fails the owner-crash-before-assignment schedule. It is a failed sub-route under crash containment, not proof that jobs are impossible. The job-at-creation contract is the proposed answer. Do not fall back to the unsafe sequence if job-list creation is unsupported or fails.

## Descendant ownership and observed completion

For ordinary `CreateProcess` descendants, a non-breakaway ancestor job preserves membership even after the original parent exits, and nested jobs remain subsets of their ancestors. Descendant creation after the last inventory therefore does not create a discovery race. Existing enclosing jobs may impose stricter limits or reject valid nesting; launch must fail with owned cleanup rather than enabling breakaway or relaxing containment. A descendant may use its own nested job without leaving the controlling ancestor. [Nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

Membership is not universal attribution. Microsoft explicitly excludes children requested through `Win32_Process.Create` from ordinary inheritance; external brokers and deliberately reassigned parentage need separate analysis. This route must prove that the pinned browser and required task processes create their owned descendants within the admitted job mechanism. It cannot claim arbitrary hostile or externally brokered descendants are covered merely because a job exists. That is a native admission obligation, not a changed no-orphan requirement. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Cleanup first latches stop and stops new work. Context/page closure and attachment disconnection remain joined, including late handles. When escalation is required, its existing trigger calls only `TerminateJobObject(hJob)`. That operation targets the processes in that job and child jobs, irrespective of numeric PID reuse. It cannot select foreign replacement 222 solely because the old root had PID 222. Root handle release does not surrender descendant membership. [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

After termination requests, retain the job handle and repeatedly obtain successful `QueryInformationJobObject` accounting observations until `ActiveProcesses == 0`, while draining root wait and all owned pipes/I/O. Close the original root handle once its wait completes, and prevent new external assignments. A job-completion-port notification can wake the observer, but never certifies zero by itself. Microsoft does not guarantee delivery of general job notifications, and a job handle's signaled state is documented for job-time-limit termination, so neither a missing message nor an ordinary wait-on-job shortcut is the drain oracle. [QueryInformationJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject), [accounting fields](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [job notifications and lifetime](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Only an authoritative zero observation after owned creation has settled and stopped can be final. Query failure means unknown. A hung I/O drain means pending. The process may outlive the 120-second work deadline while disposing; it must continue to report non-final state and preserve ownership. Closing the last job handle is the owner-death backstop, not an observed successful receipt. A leaked inherited job handle defeats that backstop, which is why job-handle inheritance is forbidden.

## Required controls before candidate admission

| Bound | Required proof |
| --- | --- |
| Existing contract | Unchanged original 22 + 11 checks, Review51 late-child schedules, exact identity/date checks, failure statuses, late listen/acquisition/disposal joins, no early final receipt. |
| Exact SDK routes | Preserve current Review54 red traces; show candidate has no `launchProcess`/BrowserServer PID-stop path on success, timeout, rejection, signal and repeated close; execute actual candidate bodies. |
| Native creation | Membership before initial execution; job-list failure; direct assignment-refusal rescue control; cancellation at every acquired-handle boundary; unexpected `ResumeThread` outcomes. |
| Owner loss | Terminate owner before creation, during creation, after creation before resume, during work and during disposal; no suspended or running owned child remains. |
| Nesting/breakaway | Existing enclosing job, permitted nested browser jobs, denied nesting, explicit and silent breakaway mutation controls, no automatic fallback. |
| Descendant class | Root exits before observation with surviving child/grandchild; child creation during shutdown; known-subset emptiness stays separate from observed job zero; foreign sentinels untouched. |
| Native failure | Failed terminate, failed zero query, pending process exit, lost notification, delayed pipe close, leaked job-handle mutation, profile removal refusal, SDK attach rejection and transport-close failure. |
| API and pixels | Dedicated inherited pipe authenticity/framing, exact argument/binary pins, `newContext`/CDP session/page flows, controller unchanged, full 36 synthetic shots then separately authorized 44 native hardware frames with inspection. |

Portable failure messages must name the operation and executable or profile, include the Win32 error and observed cleanup state, and state the supported recovery. Examples: `Owned Chromium launch requires Windows 10 job-at-creation support; no browser was created. Use a supported host.`; `AssignProcessToJobObject failed for the dedicated Chromium process (Win32 5); original-handle termination is pending, so this run is not final.`; `QueryInformationJobObject failed (Win32 N); descendant disposal is unknown and the owned job remains open.` A clean native stop does not erase the capture failure that triggered it.
