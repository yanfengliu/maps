## Smallest proposed implementation boundary

Propose one Windows C++ Node-API addon, a thin ESM object implementing the public `ConnectOverCDPTransport`, the proof case runner, and a **test-only** native outer driver/pipe peer. There is no new production helper process, runtime, broker or dependency framework. The addon owns Chromium in-process. The outer test driver extends the retained native fixture's creation/drain mechanism only to launch the pinned Node worker and provide the three pipe controls below. Its changed executable parameter and I/O adaptations require new exact-source review; the old fixture's acceptance does not transfer automatically.

The existing proposed surface remains `beginOwnedBrowser(spec) -> { ready, requestStop(reason), drained }`. Register the scope and all promises before asynchronous work. The native ledger owns job, original process/thread handles, pipe ends, operation buffers/events, worker thread and callback queue. Every acquisition is inserted immediately, before another fallible operation or cancellation check. `ready` rejection or late success never removes it. `requestStop` is idempotent and means only stop requested. `drained` returns the observed fields and retained error list; completed cleanup with an earlier error is not a clean result.

Use the actual public `chromium.connectOverCDP(transport, { artifactsDir: ownedCaseArtifactsDir, timeout: 30000 })` overload, leaving noDefaults and slowMo at their existing defaults. The installed public types expose artifactsDir at lines 25512–25516; the retained client forwards it, and the retained server skips its own mkdtemp when it is supplied. Pre-create and register that exact artifacts directory with the owner. The owner removes it only after SDK settlement and native closure, since the SDK does not own this supplied directory. This prevents an unregistered SDK temporary-directory acquisition from preceding the browser scope.

Create two connected, byte-mode named-pipe pairs before process creation. Parent endpoints are the servers: outbound command pipe and inbound reply pipe, both with FILE_FLAG_OVERLAPPED. The owner's child-end clients use GENERIC_READ and GENERIC_WRITE respectively without FILE_FLAG_OVERLAPPED, because Chromium passes null OVERLAPPED. Use one instance, FILE_FLAG_FIRST_PIPE_INSTANCE, PIPE_TYPE_BYTE, PIPE_READMODE_BYTE, PIPE_WAIT, PIPE_REJECT_REMOTE_CLIENTS and unique fixed per-run/per-case names. Both endpoints are opened by the owner before inheritance; GetNamedPipeClientProcessId on each server must identify this still-live owner process. That identity check validates this connection, not cleanup authority. A name collision or foreign connection fails without choosing another name. Pipe names are not CDP discovery endpoints and are never passed to Playwright. [Microsoft pipe contract](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew).

Only child command-read, child reply-write and explicit stdin/stdout/stderr handles enter `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Stdin is dedicated NUL; stdout/stderr use dedicated owned logs. Parent pipe ends, job, process, controller and outer-rescue handles are excluded and non-inheritable. Serialize only valid, non-pseudo child pipe handles whose uint32 round trip is checked. Attribute arrays and values outlive attribute-list destruction. Close parent copies of child ends after creation and attribute cleanup, while retaining every failed close for later joining.

Create the exact executable with explicit `lpApplicationName`, correctly quoted argv, `CREATE_SUSPENDED | EXTENDED_STARTUPINFO_PRESENT | CREATE_NO_WINDOW`, and private job supplied by `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Verify KILL_ON_JOB_CLOSE, absence of both breakaway flags and exact membership before the single resume. No post-create assignment fallback exists. Retain original creation handles immediately; never reopen by PID or call taskkill. Preserve known failure, late-acquisition, owner-loss and outer-rescue contracts from Reviews56/61/63. Outer rescue surrounds the Node owner and its descendants at creation but does not hold the inner job. It scores before rescue, waits retained authorities, and cannot emit candidate success after owner loss.

## Framing, callback timing and drainage

Use UTF-8 JSON plus one zero byte. Accumulate bytes until each delimiter before decoding, so a multibyte sequence split across reads is safe. Preserve ordering and every complete message; reject malformed/truncated data with operation and source details. Serialize outbound writes, retain each buffer until its native operation settles, and distinguish accepted, written, canceled and failed messages. The proof payloads and exact lengths are fixed in `proposed-checks.json`; they are not a new whole-capture size limit.

The callback requirement comes from **installed Playwright**, separately from Chromium's C++ framing. `CRSession.send` calls transport.send before registering its pending callback. Deliver every inbound message on a later JS turn, including already buffered replies. The retained connection fragment is `427ece8f2893d698f267bbde770da232f0dda86180c5320242c44102c56ffb60`. Chromium's attach path installs callbacks before the first request but does not invoke optional transport.open. Do not depend on that hook. Queue messages until onmessage is installed; give them one ordered deferred delivery path. Once terminal state is reached, stop new sends and deliver onclose once after earlier complete messages, replaying it asynchronously for a late subscriber. Native/JSON/callback failures are recorded outside the SDK before reporting disconnect; no uncaught callback or swallowed SDK exception becomes cleanup success.

The addon uses an owned native I/O worker and a referenced Node-API thread-safe callback channel, not polling the JS loop. Keep native buffers alive until completion and callback payloads alive until consumed or explicitly discarded during environment shutdown. A Node asynchronous cleanup hook latches stop and joins native work before removal; it cannot depend on JS running after environment teardown. Node-API teardown is proposed, unimplemented and requires review and actual exercise. [Node24 API contract](https://nodejs.org/download/release/v24.12.0/docs/api/n-api.html#napi_add_async_cleanup_hook).

Use a distinct OVERLAPPED/event/buffer per active read and write. Stop new scheduling before cancellation. `CancelIoEx` is only a request: preserve success/error and wait for each operation's actual completion, including normal-completion races and ERROR_OPERATION_ABORTED. ERROR_NOT_FOUND is not itself proof of completion. Reclaim storage only after the completion is observed. [Cancellation contract](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex), [completion contract](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getoverlappedresult).

Keep separate records for acquisition stopped/settled, original root wait, successful job-zero query, each I/O terminal result, stream EOF versus intentional cancellation, native handle closure, worker/callback-channel closure, SDK operation settlement and profile/artifacts removal. `transport.close()` latches stop synchronously; the thin owner independently awaits native drainage. SDK browser.close/onclose is never that receipt. Retain primary and cleanup errors before callbacks because the installed SDK's failed-attach catch can swallow a transport-close exception. Notify protocol close when no further protocol delivery is possible; native disposal may still be pending, which must remain explicit. This avoids making SDK disconnect wait on a cleanup operation that itself awaits the SDK.

The caller registers every started attach/context/page/session operation. Late returned values are recorded before checking stop, then closed and joined. Stop admits no new user work. A 120-second work deadline triggers the same stop path and failed work status; it does not abandon drainage or promise a hard process-return deadline. Directory removal follows native closure and SDK settlement. A failed removal stays in the error ledger even if a later retry succeeds. No original build/server behavior is replaced; those resources are absent from this bounded proof and remain later obligations.
