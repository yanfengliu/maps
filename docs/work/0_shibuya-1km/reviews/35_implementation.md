## Non-blocking findings

### 1. (high, record) The crawl failure branch cannot fire at the span this lane achieves, and the record describes the flaw as making the bound merely "looser"

`tools/flicker/judge.ts:504-505` is `const allowed = contract.crawlFractionPerFrame * Math.max(1, pair.frameGap);` then `if (!pair.shiftAtSearchBoundary && pair.crawl > allowed)`. Since `pair.crawl` is `unexplainedFraction / frameGap` (`:602`), the predicate is exactly

> fail iff `unexplainedFraction > CRAWL_FRACTION_PER_FRAME × frameGap²`

so the bound on the fraction of the frame the judge will tolerate is **quadratic in the span**: 0.125 at the fixture's 5-frame span, 0.18 at 6, 0.72 at 12, **2.53 at 22.5 and 2.645 at 23**. Measured spans from `capture/manifest-{orbit,ascent}.json` are 22, 22, 22, 22, 22, 22.5, 23, 23, 22.5, 22.5 and 21.5, 20.5, 21.5, 22, 21.5, 21.5, 21, 23, 22.5, 22, 22 — every one of them past `sqrt(1/0.005) = 14.14`, where the predicate would need **more than 100% of the frame** unexplained. It cannot fire, and has never fired, in any real run of this lane. The synthetic control fires only because the fixture's span is 5 (`judge.ts:112`, `test/flicker-frames.ts:75-76`).

What the record says instead: the report calls the flaw "a *slower* screenshot makes the bound looser … the same content at a 23-frame span is allowed 0.115 of the frame, at RUN-01's 6-frame span only 0.030" (`RUN-02-REPORT.md:126`), `quality-register.md:23` repeats that form, and `local-rules.md:155` lists "the crawl bar exceeded" among the failure classes "each been made to go red" — which was done at a span the lane never reaches. The judge's own failure message (`judge.ts:507-509`) quotes `1.150e-1`, 85× the worst measured rate, so "3.7× under the shipped bar" (`RUN-02-REPORT.md:107`) compares the reported number to a constant the judge does not apply to it.

The lane is right that the number is now a measurement: I re-derived every pair from the PNGs (below). The defect in the *form* is pre-existing and disclosed; the defect in the *description* is new and understates it. **Disposition:** acceptable to carry unfixed, as the register prescribes; not acceptable to carry as "looser". One sentence in the report and in `local-rules.md:157` — "at a span s the predicate requires more than `0.005 s²` of the frame to be unexplained, so it cannot fire past 14 rendered frames" — closes it. If any later document cites this run's `no failures` as the crawl class passing a gate, that citation is a blocking error.

### 2. (high, record) The recorded mechanism of the `channelDelta` defect is false, in four places, one of them a tracked register entry

`tools/flicker/judge.ts:684-690`, `RUN-02-REPORT.md:39`, `docs/learning/defect-register.md:7,9` and `quality-register.md:26` all explain the defect as: the pixel indices "run to 921,599 against a 3,686,400-byte array", so `Uint8Array` returns `undefined` past its end, `Math.abs(undefined - undefined)` is `NaN`, every comparison is false, and the function fell through to a channel byte.

That cannot happen, at any frame size, for any RGBA buffer: for W×H pixels the array is 4WH bytes and a pixel index is at most WH−1, so `index + 2 < 4WH` always. Measured on the lane's own bytes (probe `rederive.scratch.test.ts`): `array bytes 3686400, pixels 921600, largest pixel index 921599, in bounds: true`, and the mutation returns `changedFraction 0.9702300347222222` — **finite**, no `undefined`, no `NaN`. The reads land a quarter of the way into the picture and compare unrelated pixels, which is why the number is wrong; there is no exception path and no out-of-bounds path to argue about.

The same paragraph's root cause is wrong in the same direction. "a missing unit conversion that every unit fixture in this repo is structurally unable to reach, because their frames are too small to index out of bounds" — the 192×108 fixture *does* produce the wrong number: the same mutation makes `movingRecord(10)` read `0.9929824561403509`, and `test/flicker-judge.test.ts:91-94`'s pre-fix assertion was `expect(pair.changedFraction).toBeGreaterThan(0.5)` — an assertion written to the bug's own output, which the buggy value satisfies. What hid the defect was an assertion agreeing with the defect, not a frame that was too small; the generalisable lesson is the repo's own "a check built from the same symbol as the thing it checks proves only that the code agrees with itself", and it is a stronger lesson than the one recorded.

The gate itself is sound and the fix is right — see "What I verified holds". **Disposition:** correct `judge.ts:681-693`, the `gate-proofs.md` bound at `:1367`, the defect-register entry and the register row; the wrong mechanism is now the standing account in the file whose job is to be the standing account.
