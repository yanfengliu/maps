## Reports

### Independent mechanism judgment

**Accept A's restricted negative proof. Recommend B only for a small native ownership proof, with explicit conditions below. Neither design is accepted as a repaired launcher, and native capture remains blocked.** Root/known handles plus finite live snapshots cannot supply the missing ancestry edge. B supplies a different source of authority through kernel membership at creation, but that authority and its pipe boundary have not run here.

A's proof is valid under its named information restriction. Consider two histories with the same owned root and unrelated parent visible before a sample gap. During that gap, intermediate 333 is created by root 222 in one history and unrelated parent 999 in the other. It creates leaf 444 and exits before the next sample. Both roots, every observed creation time, executable and command field, every later live row, and every already-retained handle result can be identical. Only the hidden parent edge differs. Killing the leaf is foreign termination in one history; leaving it is an orphan in the other. An honest pending result does not establish successful disposal. Additional live snapshots cannot reconstruct that vanished edge. The independent checker constructs these histories from process records in eight separate sample gaps and derives their equal observations, rather than sharing one prebuilt observation object.

This is an information limit, not a proof that every process-supervision strategy fails. A complete birth stream, a creation barrier or kernel membership changes the premise. The result also assumes no separate unforgeable ownership channel; matching profile-like text and executable names are not such a channel. Holding the original root handle remains useful: Windows keeps the process object and its PID while a handle remains, but it conveys no authority over an unobserved child. [Microsoft PID lifetime explanation](https://devblogs.microsoft.com/oldnewthing/20110107-00/?p=11803). Do not spend another v4 implementation pass adding only root retention or more snapshots, and do not reject all retained-handle strategies from this proof.

B's two parts are inseparable. Assigning a private non-breakaway job during `CreateProcessW` removes the suspended-before-assignment owner-crash window. Microsoft documents that exact window and its job-list remedy. Creating suspended and assigning afterward is an unsafe fallback under the owner-loss requirement, even if ordinary assignment failure has a handle-based rescue. [Microsoft creation mechanism](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812). The creation contract must preserve the returned original process/thread handles, job and attribute storage through all failure paths. The attribute values must remain alive until the attribute list is destroyed, which is a more precise lifetime than merely until `CreateProcessW` returns. The inherited handle list needs explicit inheritable pipe ends and `bInheritHandles=TRUE`; job and controller handles must be absent. [Creation attribute contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

A job around unchanged BrowserServer fails F30. The SDK can still invoke numeric-PID `taskkill` against an unrelated replacement; its own membership does not constrain that target. B instead uses the installed public custom transport. I checked the real public path, beyond B's extracted `_connectOverCDPImpl` model: `coreBundle.js:63361-63400` forwards the object to the local dispatcher, and `43075-43158` gives the browser a close/kill object that closes that transport. The installed core digest is `549070af3acabb3efcc4f55bfe6210f9f7c2fcf633cf7eaa59bfe60719969171`.

Four controls execute the actual installed public API with all Node spawn/exec/kill entry points forbidden. Attach, new context, browser CDP session and repeated close pass without a native call. Attach rejection calls transport close. Crucially, when the synthetic close throws, the public API returns the original attach error and the transport remains unclosed until the test owner's separate rescue. The close failure is swallowed on that SDK path. In another arm, public `browser.close()` remains pending until `transport.onclose` fires. That callback is still a protocol event supplied by the transport, not native process or I/O evidence. These results support B's separate owner ledger; they would reject any implementation that interprets SDK rejection or disconnect as a drainage receipt.

Register that owner ledger before scheduling native acquisition. `ready` rejection, timeout and cancellation must not discard the scope. Every late browser/context/page/session or native handle must be recorded before testing cancellation; every started disposal must remain joined. A stop request is idempotent and does not resolve drainage. Native close failures must be retained out of band because the SDK can hide them. Closing pending native I/O requires completion/cancellation to settle before releasing its backing storage or handle. Removing a profile/artifacts directory must be observed separately and retain any failure. Build children, delayed HTTP listen and HTTP connections remain outside a browser-only job receipt and retain their existing joins.

For successful completion, B must stop future acquisition/assignment, observe successful job accounting with zero active processes, wait the original root, settle all native I/O, close its handles and join the SDK and directory/server work. `TerminateProcess` is asynchronous and therefore requires a wait on the original handle; a termination request cannot substitute for that observation. [TerminateProcess contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess). Notification delivery alone is insufficient, and a failed accounting query remains unknown. Owner-death `KILL_ON_JOB_CLOSE` is a containment backstop; no code remains to emit a successful receipt after its owner dies. A deliberately leaked job handle must make the owner-loss control fail. [Job lifetime and notifications](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Membership also has a real limit. Normal descendants remain inside the ancestor job, including children of nested jobs; nesting can be refused by the enclosing environment and must fail without enabling breakaway. [Nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs). External brokers such as `Win32_Process.Create`, or a deliberately selected outside parent, can create a task-related process outside this containment. [Job inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [parent-process attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). B openly acknowledges this gap. A successful job-zero test cannot silently change acceptance to only processes that happened to join the job. Before browser admission, the pinned launch configuration needs a concrete descendant-creation account and an escape control that remains red; observed escapes require a different ownership mechanism or a reviewed cause-specific repair. No evidence here proves that the pinned browser uses such an escape, or proves that it never does.

### Smallest useful next proof

Recommend one separately authorized, headless native ownership primitive with a deliberately small fixture process tree, without Chromium, CDP, scene data or capture. Its purpose is to test the missing OS boundary before paying for pipe and capture integration. Use the same native create/stop/wait/drain code intended for the eventual boundary, with owned fixture executables and an outer test owner holding original rescue handles. A new helper runtime or framework is not part of this admission. Check toolchain prerequisites and freeze the source, executable digests, command line, operating-system build, test cases and expected reds before execution.

The acceptance for that proof is six causal schedules: (1) membership is observed before the initially suspended root runs; (2) the root creates child and grandchild then exits before the observer samples, and stopping the job disposes the survivors while an outside sentinel survives; (3) a child starts during the controlled shutdown boundary and is included or creation is refused, never silently omitted; (4) stop/cancellation arrives at each native handle acquisition boundary and all acquired resources are joined; (5) the owner is terminated before creation, while creation is pending, before resume, during work and during drain, with no surviving owned fixture process; (6) creation, membership/query, resume, termination and drain refusal produce retained errors and honest nonfinal state rather than an invented clean receipt. Test the actual enclosing-job environment and one nested fixture job, including refusal with no breakaway fallback. These are a primitive proof's schedules, not substitutes for the original 22+11 launcher cases.

The proof must have discriminating negative controls: post-creation assignment stranded by owner death; leaked inherited job handle; breakaway enabled; and a held pipe whose process population is already zero. Observe each negative before its outer fixture owner rescues it through retained original handles. The observer must not hold another handle to the job whose last-handle owner-loss behavior is being tested. For creation-time crashes before handles can be returned, use a separate outer rescue job created atomically around the fixture owner; hold only that outer job and the original fixture handles, and do not terminate it until after recording the inner mechanism's verdict. Its inherited containment is a test guard, not evidence that the inner job worked. Rescue is cleanup, never candidate success. Do not force numeric PID reuse or use broad taskkill. A same-number replacement remains the Review54 source-model counterexample; the candidate must lack the unsafe numeric stop route entirely. A harness timeout may report that the experiment failed, but must not abandon its owned fixtures or issue a final cleanup receipt while draining. Record the exact crash boundary reached; an unobserved intended interruption point is unavailable coverage, never a passed case.

Read-only capability checks found Windows `10.0.26100.0`, Node `v24.12.0`, and a VC Tools installation returned by `vswhere` at `C:/Program Files (x86)/Microsoft Visual Studio/18/BuildTools`; Windows SDK headers are present. `cl`, `clang`, `clang-cl`, `gcc` and `cmake` were absent from this shell's PATH. This is discovery, not a compiler test or proof that the current enclosing job permits the mechanism. No install is needed merely on the evidence of PATH absence.

If that proof passes and receives independent review, the next separate proof is native CDP-pipe interoperability with the exact pinned Chromium executable and launch vector. Pin the installed default argument generator and current `--use-gl=angle`, `--use-angle=d3d11`, `--disable-lcd-text`, headless mode, profile and sandbox behavior; preserve context viewport `1280x720` and scale 1. Verify Windows inherited fd 3/4 mapping, framing, callback timing, transport rejection and pipe drain through the actual public SDK. Source-model tests cannot establish this. CDP attachment has lower fidelity than Playwright's own protocol, so successful attach alone does not admit the unchanged page/controller flow. [Playwright CDP contract](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp).

Only then should a frozen launcher successor execute the original 22 lifecycle plus 11 candidate checks, late-acquisition and descendant schedules, Review54 reds and exact identity/date guards without reducing assertions, statuses, timers or denominators. Any necessary API adapter in the instrument needs independent review, while old exact-body controls stay reproducible. Keep the original 36-shot synthetic controller and helpers unchanged. The later native 44-frame adapter and its inspection need their own root admission. The 120-second limit remains a work deadline; incomplete drainage remains visibly nonfinal for as long as required. No stage below whole acceptance may emit a whole-cleanup or capture certificate.
