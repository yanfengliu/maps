## Findings and disposition

**F35 — high priority, open: environment teardown has no scheduled discriminator or explicit cleanup dependency order.** Root reserved F35 for this review. Target: design line43, lines53-66 and line80; `proposed-checks.json:8-20`. The proposed addon owns live native work and a referenced thread-safe callback channel. It promises a cleanup hook that works after JavaScript becomes unavailable and says that behavior requires actual exercise. Every listed trigger instead runs requestStop, SDK close or peer exit while the addon environment remains usable. C05's held ready result and N02's cancellation do not change that. Merely listing teardown among later unknowns does not assign it a case or explicitly defer the contract from the first proof.

[Node24.12.0's documented contract](https://nodejs.org/download/release/v24.12.0/docs/api/n-api.html#finalization-on-the-exit-of-the-nodejs-environment) permits environment teardown with JavaScript disabled, schedules finalizers after manual cleanup hooks, and permits queued thread-safe callbacks with null environment/callback values. A referenced thread-safe function keeps the loop alive. Those facts make ordinary JavaScript stop insufficient evidence for teardown and make a cleanup hook that waits on JavaScript or a later finalizer a possible cycle. This review identifies the missing contract, not proof that the unimplemented addon already has such a cycle.

The smallest recommended amendment is:

1. Preserve C01-C07 and N01-N03, adding a separately counted N04 for actual addon-environment teardown. A test-only Node Worker hosting the same addon while its parent environment and outer owner remain alive is one suitable design to specify and review. Use a native peer, not another browser or SDK attempt. The resulting proposed denominator would be 11 total: seven Chromium cases, six SDK attach attempts and four native controls. Do not silently absorb another execution into N02's count.
2. Reach and independently record pending native read/write ownership plus queued callback payload ownership before triggering teardown, without first calling the ordinary JS stop path. Observe cleanup-hook entry, actual operation settlement, payload delivery/discard accounting, worker exit, callback-channel finalization and retained-handle closure through native receipts available outside the destroyed environment. An empty queue or already-drained operation cannot satisfy these checkpoints. Whole-process termination or OS handle cleanup would exercise the prior owner-loss boundary, not this Node environment hook.
3. Specify the shutdown dependency order: latch stop and reject new work; stop callback production without waiting for JS; cancel and settle I/O while storage remains owned; join the producer; retire payloads and channel ownership under an explicit native lifetime rule; remove the async hook without waiting for a finalizer whose scheduling depends on completing that hook. State which native owner survives until the last callback/finalizer access. Account for queue-full/closing results and prevent use after a producer releases its channel authority. These are proof obligations for the implementation author, not an approved API-call recipe.
4. Extend C01's normal-close acceptance to include the child Node process returning naturally after the owner drains, with its actual exit receipt. This checks the referenced callback channel does not keep an otherwise finished case alive. N04 must likewise distinguish environment completion, still-live host, original peer/root wait, job zero, every I/O/storage result and any rescue. Do not require a destroyed environment to settle JS promises; mark their disposition truthfully and use the independent native receipt for teardown. A deadline or unavailable receipt leaves a nonfinal/failing case and retained rescue authority.

Root agreed with this bounded amendment direction during review. F35 remains open until the author freezes a revised design, case roster and cleanup ordering for focused re-review. No other new material finding was allocated. Node header/library acquisition remains separately unadmitted; source header declarations are not a prepared addon kit. The proposed direct MSVC build against exact Node24.12.0 x64 headers/node.lib is a stated prerequisite route, not verified compatibility.
