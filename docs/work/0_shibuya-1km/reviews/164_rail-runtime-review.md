### R164-O2 — P2: the near-plane intersection does not use the bound projection

`src/harness/rail-camera-clearance.ts:56` unprojects the four actual near corners, but line 96 recomputes a symmetric half-width/height from FOV and aspect, and lines 127–129 use those different limits. All three vertices project inside the canvas, at X approximately 0.648–0.756 and Y ±0.096 in NDC, with Z −1. The observer nevertheless returns `eligible: true`. ### R164-O3 — P2: interleaved position updates retain a stale broadphase box

`src/harness/rail-camera-clearance.ts:40–42` reads `attribute.version`. Three's `InterleavedBufferAttribute.needsUpdate` increments `attribute.data.version` instead (`node_modules/three/src/core/InterleavedBufferAttribute.js:101–103`). The observer accepts that attribute and keeps its cached parts at version zero. A remote triangle initially clears; moving its interleaved positions onto the near rectangle and setting `needsUpdate` still returns clear with zero broadphase groups. A fresh observer over the identical changed geometry finds the intersection. Bind the backing buffer identity/version, or report this unsupported storage before using cached bounds. The ordinary BufferAttribute refresh control already present in the product test still passes.

### R164-O4 — P2: material groups are not traversed with renderer draw semantics

`src/harness/rail-camera-clearance.ts:43–49` walks one triangle sequence from `drawRange.start`, then chooses the first group containing the first index. Three separately intersects each rendered material group's start/end with drawRange and begins triangle assembly at that effective start (`node_modules/three/src/renderers/WebGLRenderer.js:1122–1138,1784–1802`). The control uses a material-array mesh with one group `{start:1,count:3,materialIndex:0}`. The renderer's actual triangle crosses the near rectangle. The observer inspects a different triangle and returns clear. Replacing only the fixture geometry with the actual drawn triangle produces the expected intersection. The same implementation also treats faces outside all array-material groups as material zero, causing conservative false refusals. Match the actual draw sequence or refuse non-supported groups/ranges rather than silently reinterpreting them.

### R164-O5 — P2: an unsupported after-render callback is accepted

`src/harness/rail-camera-clearance.ts:73` checks only `onBeforeRender`; line 85 checks the material's before-render callback. An object with custom `onAfterRender` remains eligible, despite the contract refusing unrecognized render callbacks before broadphase. The installed renderer invokes this callback at `node_modules/three/src/renderers/WebGLRenderer.js:2030`; it can change source transforms or geometry after the drawn frame. The far-box control supplies a custom callback and returns clear instead of unknown. The observer does not execute it, which is correct, but must refuse it or establish a specifically reviewed non-mutating exception. Current source contains no such callback, so this is a missing enforcement boundary rather than a claimed present camera collision.
