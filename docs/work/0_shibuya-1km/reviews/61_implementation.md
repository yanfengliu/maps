The handle identity chain is grounded in creation handles. Source lines 161–168 retain the root process handle returned to the owner and publish that value before the owner checkpoint. Lines 460–476 use the runner's already-held original owner process handle as `DuplicateHandle`'s source process. The root pair obtains a non-inheritable SYNCHRONIZE-only duplicate. The descendant pair first obtains PROCESS_DUP_HANDLE plus SYNCHRONIZE on that original root, then duplicates the root-held original child handle with SYNCHRONIZE only. No PID is opened or used to select a stop target, and no tested inner-job handle is exported to the runner. Microsoft documents that duplication requires PROCESS_DUP_HANDLE on the source process and produces a handle to the same object. This supports the chain under the inspected held-source lifetime, not the scalar mailbox value alone. [DuplicateHandle contract](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle).

The child transfer avoids the push-and-publish leak window. Source lines 243–250 hold the returned child handle in a local `Handle`, publish it, mark creation successful, then wait for a separate acknowledgement. Lines 447–449 ledger each successful local duplicate before output or any following API call. The child acknowledgement occurs only after the final target is owned at lines 473–475. The child source can then close its original handle without changing the duplicate's referent. The acknowledgement uses its own interlocked field; it neither waits on nor signals the owner's original auto-reset advance event. Publication uses interlocked release and read barriers around the handle scalar. The Microsoft contract states that the interlocked exchange supplies a full memory barrier. [InterlockedExchange contract](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-interlockedexchange).

These are cooperative, single-run fixture mailboxes, not an authenticated IPC mechanism for hostile writers. The owner checkpoint still has its existing 30-second wait; the source holds its root handle while stopped there, and failure to remain at the cut can make transfer fail. This review does not grant a general source-lifetime guarantee after arbitrary external interference or suspension. Within the inspected fixture, no new root-handle allocation/reuse path was introduced after its close. The child barrier retains its original process handle until acknowledgement or process disposal by the enclosing rescue job. It cannot falsely declare successful transfer merely because a timeout elapsed.

The breakaway observer targets the created descendant, not the root that should die with the inner job. The matched candidate uses the new `contained-child` role to actually create and resume an ordinary descendant. `childResult == 1`, publication and a live pre-cut wait are required; creation refusal cannot stand in for successful containment. The suspended post-assignment root is observed through its original process handle and is not required to execute an acknowledgement. Microsoft documents immediate state sampling when the wait interval is zero and requires SYNCHRONIZE. An unsignaled result establishes non-termination at that sample; it does not prove continuing application progress. [WaitForSingleObject contract](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).
