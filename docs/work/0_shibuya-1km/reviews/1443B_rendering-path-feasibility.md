## Decision

BOUNDED NEGATIVE: this audit establishes no shared rendering/import defect whose correction can presently be claimed to deliver the required obvious improvement across three separated fronts. The source supports photographic contrast and geometric face normals; it does not supply the spatial material or illumination information needed to turn that photograph reliably into detailed light-responsive glazing/recesses. This finding closes only this audited evidence path as a demonstrated ready increment. It does not prove rendering improvements impossible, close a final criterion, or establish a global blocker.

A contrast-preservation experiment remains UNDEREXPLORED, not a recommended implementation or a demonstrated depth solution. The current operator destroys some source distinctions, but the evidence does not bind those distinctions to three exposed fronts or establish that preserving the photographed shadow is the correct material response. More saturation, global sharpening, and albedo-derived normals would not remedy that missing authority.

## Actual production/source path

1. tools/scene/build-buildings.ts uses parseB3dm/parseGlb, placement and serialization. tools/tiles/b3dm.ts preserves the embedded texture payload while rewriting placement. The inspected source is the regular cached data/scene/buildings/data/*.b3dm that /scene/ serves, not a replacement image or higher-resolution alternate.
2. src/scene/buildings.ts registers GLTFExtensionsPlugin and FacadeTexturePlugin before resource accounting. The installed GLTFExtensionsPlugin imports three/addons/loaders/GLTFLoader.js. That actual loader assigns baseColorTexture with SRGBColorSpace (GLTFLoader.js:3658), takes authored scalar roughness/metalness, and would bind normal/metallic-roughness maps if present. The three selected tiles have POSITION, NORMAL, _BATCHID and photographic TEXCOORD_0. Absence of a normal map is not absence of geometric normals.
3. The 67 tiles contain 132 materials, 65 base-color map references and zero normal, metallic-roughness, occlusion or emissive maps. This counts material references, not distinct semantic facades. Photographic source materials commonly specify roughness about 0.3 and metallic 0.5, while untextured materials have other scalars. The tile-materials.ts header saying PLATEAU supplies neither roughness nor metalness is too broad: the files supply scalar factors, but no spatial material classification. That documentation mismatch is not evidence of a renderer bug.
4. FacadeTexturePlugin validates source eligibility before rebuilding textures. facade-textures.ts:301-407 resizes the image with createImageBitmap high quality to the unchanged geographic cap, reads RGBA, derives the sign alpha mask from the pre-de-light pixels, invokes the buildings-owned AtlasDelightProcessor, then creates an sRGB DataTexture. It uses trilinear minification, generated mipmaps and anisotropy at least 8; wrap/magnification state is inherited. No missing-sRGB or missing-mipmap defect was established. Actual effective anisotropy and browser resize behavior were not measured here.
5. AtlasDelightProcessor uses NoColorSpace on its intermediate byte texture/target, explicit sRGB decode/encode, texelFetch, and disabled tone mapping. Its color-space choices match its explicit byte operator; labelling that intermediate texture sRGB would introduce an additional decode. Only code was inspected, so GPU parity is not newly established.
6. tile-materials.ts:111-116 replaces scalar material response. Its Satellite branch (:265-291) classifies dark/neutral pixels as probable glass, lifts photographic albedo, and adds near floor/frame terms, then changes roughness. Textured Satellite walls keep source geometric normals apart from separately admitted details; the procedural style has its own relief branch. Thus a proposal to add dark-pixel glazing response generically would duplicate an existing proxy. Dark albedo alone does not independently distinguish glazing from paint or shadow.
7. post.ts uses TAA, GTAO, bloom and OutputPass/ACES. Moving frames use current-frame spatial samples; still accumulation depends on the application's stillness decision. No double tone-map, incorrect color encode, or TAA smear was demonstrated. Three stills cannot establish temporal sharpness or absence of crawl. GTAO cannot recover a recess absent from the geometry/normal information it receives.

## Information loss and its exact bound

The actual imported CPU operator maps neutral source byte levels 0, 5, 10, 15 and 20 to RGB 39,39,39. Input 100 becomes 110,109,106; 128 becomes 126,127,128; 200 becomes 166,167,170; 255 becomes 193,194,197. The explicit airlight subtraction, compression exponent 0.6 and linear albedo floor 0.02 are the causes, not an accidental sRGB omission. Compression without clipping scales log-luminance contrast by 0.6; clipping/quantization is not invertible. These are arithmetic observations, not measured material truth.

source-image-metrics.json independently decodes embedded WebP using Pillow 12.2.0/NumPy 2.4.2, retains their SHA-256 and gives native 4096x4096 atlas-wide dark counts. data488/data498/data518 contain respectively 3,838,439 / 4,446,313 / 2,669,288 pixels with all RGB channels at most 20. These populations include unoccupied atlas padding and unrelated roof/wall charts. They do NOT measure visible/frontage pixels, exact neutral rows, the post-resize browser input, or perceptual lost detail. Do not turn these large counts into an exposed-facade coverage claim. data518 is the one admitted native 4096 leaf; the others remain subject to their unchanged cap.

An independent physical expectation is missing: no calibrated albedo/irradiance pair, shadow label, glazing/paint mask, measured roughness field or recess normal/depth map is present in these inspected inputs. A photograph contains useful edges but an edge need not be a material boundary or recess. Inferring geometry/roughness from it remains an authored proxy requiring separate source and visual review. No shader can restore details already removed by the cap or source capture.

## First discriminator if root elects another rendering probe

Before an implementation, use existing controls/harness and the fixed current recipe to bind three separated exposed fronts to exact source tile/UV charts at their unchanged cap; exclude padding and identify genuine glazing/paint/sign boundaries from admitted source evidence. Inspect raw versus current processed samples from those same charts. If the collapsed distinctions are only padding, captured shadows, subpixel content or absent in the capped input, stop the contrast-recovery route for these fronts.

Only if exposed useful source distinctions are established, compare the existing production option delight:null against the unchanged operator as a bounded mechanism test through the actual plugin, with sign mask, material shader, cap, seed, camera, lighting and post unchanged. That isolates the de-light treatment as a whole; it does not prove physical albedo recovery or isolate its individual stages. Reject unless obvious coherent improvement is present across all three fixed-view fronts, the lower ordinary approach and complementary block evidence, with source/sign/noon/dusk preservation and an untuned held-out approach. A darker or more saturated image alone fails. No such GPU test or candidate was authorized/executed in this pass.

This discriminator requires native appearance evidence and a source-labelled visible population; an atlas histogram or self-derived shader oracle cannot replace either. It may return a useful contrast-only result, but has no basis yet for a shared recess/glazing-depth claim. Root should not schedule a broad shader rewrite based on this negative source audit.
