## Actual client source and causal bounds

The inspected installed code is bound to both saved source maps. Source-content UTF-8 hashes exactly match PRIMARY `three/build/three.core.js`, `GLTFLoader.js`, `DRACOLoader.js`, `src/scene/buildings.ts`, and the three imported `3d-tiles-renderer/build/` members. The actual minified FileLoader fetch/stream code and decoder initialization at both recorded stack coordinates were also inspected. Do not infer the executable path solely from a package's source directory.

- `createBuildings` constructs one `new DRACOLoader()` without a manager and sets `/draco/` (`buildings.ts:234–238`). `Loader` selects the global DefaultLoadingManager when no manager is supplied. GLTFExtensionsPlugin creates GLTFLoader with `tiles.manager` and supplies that already-created Draco loader; it does not reassign the Draco loader's manager. The Draco library requests therefore use DefaultLoadingManager, separately from the tiles manager and per-tile fetch signals.
- `_initDecoder` memoizes `decoderPending` and starts one wrapper-text and one wasm-arraybuffer library request; later calls reuse it (`DRACOLoader.js:320–381`). GLTFLoader's Draco extension calls `preload` (`GLTFLoader.js:2001`). Neither memoization nor FileLoader's duplicate-request table cancels the winning request. The recorded population supports one actual request for each URL.
- FileLoader creates an AbortController and combines its signal with its manager's signal. Its only explicit loader abort calls `_abortController.abort()`. No product `src/` call to `.abort()` or manager abort was found. The library FileLoader objects are local to `_loadLibrary`; DRACOLoader does not retain them or abort them in `dispose`. Draco disposal terminates workers and revokes the worker blob URL (`DRACOLoader.js:460–475`). The tile LRU callback aborts a separate per-tile controller; that signal is passed to tile fetch, not to either Draco library request. These source facts exclude those particular direct abort paths, not all possible browser cancellation causes.
- FileLoader obtains the original fetch body's reader, pumps it into a new ReadableStream, then returns `new Response(stream)` and consumes text/arraybuffer from that replacement (`three.core.js:44067–44119`). No reader cancellation or release-lock call appears in that path. A response/reader/browser lifetime issue is still an underexplored mechanism. Raw878 has no AbortSignal events, reader EOF/error observations, library fulfillment witness or browser trace that establishes it. Source shape alone cannot establish a garbage-collection cause.
- Playwright's installed Chromium `_onLoadingFailed` forwards CDP's failure text and canceled flag to `requestFailed` (`playwright-core/lib/coreBundle.js:36376–36400`). Its user-level request failure here is not an independent failure cause. CDP itself reports cancellation. `canceled: true` identifies the outcome, not the caller that initiated it.
- The body checker schedules `getResponseBody` only from `Network.loadingFinished` (`caller-diagnostic.mjs:149–164`). Its `loadingFailed` callback records a refusal without attempting that read (`:148`). Thus raw878 proves the failed row was not retained; it does **not** prove the same-session body API was unavailable for that row. This distinction does not remove the failure or establish the body hash.

Body ceilings are32MiB per resource,512MiB total and256 responses per arm. B retains272,346,171 decoded bytes across129 resources. The58,456-byte wrapper is far below the resource ceiling, and its failure path is `loadingFailed`, not a `getResponseBody` eviction/capacity error. Increasing those ceilings has no causal support from this record. Normal context closure also occurs much later and the timeline records only initial main-frame navigation, so an arm-close/new-navigation explanation is contradicted by the available lifecycle chronology.
