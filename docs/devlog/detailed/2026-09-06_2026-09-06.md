# Devlog — 2026-09-06

Phase 0 of the Shibuya deliverable: the first code in the repo. One session, one commit. Three of the four failures below had the same shape — a check that looked like it was measuring the thing it named, and was measuring something else.

## The visual gate's first run photographed another repo's app

**Timestamp:** 2026-09-06 19:15–19:32

**Action:** Ran `npm run visual` for the first time, with `vite preview` on Vite's default port 4173 and Playwright's `reuseExistingServer: !CI`.

**Result:** The run sat for ten minutes waiting for `window.__mapsHarness` and then timed out. `curl http://127.0.0.1:4173/` came back with `<title>AoE2 Prototype</title>`. A `vite preview` from the sibling `aoe2` repo was already listening on that port, and Playwright reused it rather than starting one.

**Reasoning:** Every Vite repo in this fleet previews on 4173 and serves on 5173, and several of them have a server running at any time. `reuseExistingServer` cannot tell a server it wanted from a server that happened to be there. The obvious fix — kill whatever is on the port — is wrong twice over: it destroys another participant's work, and it leaves the next collision to be discovered the same way.

Three changes instead. The preview moved to 4319 and dev to 5319, both `strictPort`, so a clash fails at bind time. `reuseExistingServer: false`, so a stale build of this app is not reused either. And `OrbitDriver.assertServingThisApp` reads a `meta[name="app-id"]` tag before anything is captured, so if the port is ever wrong again the failure names what it found instead of timing out.

**Validation:** The gate now passes end to end in about a minute. What the fix would still miss: another repo that copies the `app-id` tag verbatim, which nothing prevents.

**Notes:** Immediately after, the same port produced the opposite failure. `vite preview` with the default host bound `[::1]:4319` only, so every client dialling `127.0.0.1:4319` got a connection refused from a server that was plainly running and had logged its URL. The host is now pinned to `127.0.0.1` in `vite.config.ts`.

## The blank-frame floors were guessed, and the guess was above the real minimum

**Timestamp:** 2026-09-06 19:33–19:40

**Action:** Set `FRAME_FLOORS.distinctColours` to 150 with a comment claiming the placeholder frames measure "over 1,000", then ran the gate.

**Result:** `street-az000.png` came back with 141. Measuring all twelve gave 91 to 160 for distinct colours and 17.98 to 36.95 for luminance spread. The floors were reset to 30 and 6, roughly a third of each observed minimum, and the comments now carry the measured range and the frame it came from.

**Reasoning:** The number in the comment was never measured — it was what a colourful frame would score, applied to a scene that is entirely grey. Had it been set slightly lower it would have passed, and the repo would have carried a floor whose stated basis was fiction, right up until a legitimate change tripped it.

**Validation:** Wrapping the scene's contents in `if (false)` gives a spread of 2.84 against a floor of 6 and a worst real frame of 17.98, so the floor separates rendered from unrendered. It does not separate right from wrong, and the comment says so.

## The wheel sign was backwards and the error message caught it

**Timestamp:** 2026-09-06 19:30

**Action:** `zoomTo` computed `ticks = log(ratio) / log(0.95)` and dispatched `wheel(ticks * 100)`.

**Result:** Asked for 115 m from a start of 620 m, the camera went to 2000 m and pinned against `maxDistance`. In OrbitControls a negative `deltaY` dollies *in*, so a ratio below 1 needs a negative total, and the formula produced a positive one.

**Reasoning:** Worth a section only because of how it surfaced. The failure was not "the frame looks wrong" — it was `The controls would not reach 115 m from the target after 8 wheel corrections; they stopped at 2000 m. If the distance is pinned, the requested zoom is outside minDistance/maxDistance.` The closed loop that aims at a pose by reading the result back is what made a sign error legible instead of producing a sweep at the wrong zoom that still passed every frame check.

## Two things the gate is not

**Timestamp:** 2026-09-06 19:45–20:05

**Action:** Three deliberate mutations, each reverted: rotation disabled on the controls, the scene emptied, the canvas renamed. All three turned the gate red; the transcripts are in `docs/learning/gate-proofs.md`.

**Result:** The gate can fail, and fails for the reason the mutation targeted rather than generically.

**Notes:** Two limits a later phase should know about.

The frames are not byte-reproducible. Poses are reached to within 0.012 rad and distances to within 2%, and the damped controls settle to a slightly different residual each run, so the SHA-256 of every frame changes between runs and the distinct-colour count moves by one to three. Luminance spread was stable to a tenth across runs. Anything wanting pixel-exact goldens will have to tighten the settle tolerance first.

The WebGL-unavailable path has never been made to fire. Its message is written, its code path is reachable, and nobody has watched it happen.

## The wrong-app check was made to fire, against the real sibling app

**Timestamp:** 2026-09-06 20:00–20:20, a later session.

**Action:** Put both other halves of the fix back the way they were — `preview.port` to Vite's 4173 default, `PREVIEW_URL` to match, `reuseExistingServer` to `true` — and ran `npm run visual`. `assertServingThisApp` was left untouched, because it was the thing under test.

**Result:** No decoy was needed. aoe2's `vite preview` was already listening on 4173, so this was the original collision rather than a staged version of it. Playwright reused that server without a word, and the gate stopped in 462 ms with exit status 1 and `artifacts/visual/` empty: `Port 4173 is serving a different app, so this run would photograph that one. http://127.0.0.1:4173/ carries meta app-id absent and the title "AoE2 Prototype". …` The mutation was reverted and `git status` came back clean of it.

**Reasoning:** The check was written after the failure it prevents, so it had never been seen to reject anything, which by the canon's definition left it as code rather than a gate. Reproducing the check alone — mutating the expected `app-id` string — would have proved the comparison works and said nothing about whether the two-part failure still reaches it. It does, and it is caught before the first screenshot.

**Validation:** Four failure paths are now proved red and three are not; `AGENTS.md` and `docs/learning/gate-proofs.md` both say four rather than three. The error message was rewritten first so the recorded transcript is the one the repo now ships: it names the port, the app-id and title it found, the app-id it wanted, and what to do about it.

**Notes:** A discrepancy a later session could trip over. The heading above and the line in `docs/devlog/summary.md` say the first sweep "photographed another repo's app", which reads as twelve captured frames and a pass. The body of that same entry says what actually happened — a ten-minute wait for `window.__mapsHarness`, then a timeout, with no frames written. This run reproduced the second version and not the first. Trust the body. A wrong-app run has never produced a passing sweep in this repo, and one coordinator brief has already been written on the belief that it did.

Byte-reproducibility, re-measured for the plan: three runs of one build wrote no frame that was byte-identical in all three, with settled azimuths drifting up to 3.5e-4 rad between runs — well inside the harness's 0.012 rad tolerance, and enough to change every SHA-256.
