# The certificate did not bind the harness, and the new pointer half could not be told from a dead one

Session: 2026-09-16, a worker lane on branch `worker/gate-fixes` off `024c44d`, in the worktree `artifacts/gate-fixes/wt`, while the 44-frame verdict capture ran against the frozen revision `30c7b01` and owned port 4319 and the CPU. Both items are round 31's blocking findings — B4 and B3 — and the third change is the mis-citation the same round found.

Nothing here was verified by a gate run. `npm run visual` belongs to the capture, the two sweep specs and the hero spec cannot be run while it holds the port, and the landing is therefore reported as code plus the red controls below. What the next capture certifies is the spec-side assertions; what is proved here is that they can fail.

## B4 — nothing bound the specs and helpers that drove the browser

**What was believed.** That the certificate's `dist/` hash and scene digest covered the run: the pixels come from the build, the city comes from `data/scene`, and the plans and reviews read the certificate for which bytes and which city the frames are pictures of.

**What was false.** The instrument that drives the browser was outside both. `beginVisualRun` hashed `dist/index.html` and `dist/assets/*.{js,css}`, and `certifyVisualRun` re-derived the scene digest — nothing hashed `tools/`, so two certificates with identical build and scene hashes could have been produced by different specs, and a reader could not tell. This stopped being academic at 17:55:29 local on 2026-09-16, when `5c32286` changed `tools/visual/verify-output.ts` and added two files under `tools/visual/` while the capture that began at 17:35:33 was running. The frames are not invalidated — Playwright collects its test list and loads its specs when the run starts, and the build bytes are pinned — but the certificate could not *show* that, and `plan.md` requires "the complete source/build/data/harness closure before and after the run" of the final verification.

**What landed.** `harnessTreeDigest()` in `tools/visual/verify-output.ts`, in the same shape as `sceneTreeDigest`: the path of each file under a root and the SHA-256 of its bytes, so an edit, an addition or a deletion moves it and no timestamp, size or inode is covered. `beginVisualRun` pins `{ roots, digest, files, bytes }` into `run.json` as `harness`, and `certifyVisualRun` re-derives and compares it through `assertHarnessUnchanged` before it reads a frame — before the frame checks, beside the scene check, for the same reason. The refusal names both values and says what to do, and it says plainly that it is refusing an unbound certificate rather than claiming the frames are wrong.

**The boundary, and why it is where it is.** `HARNESS_ROOTS` is `tools/visual`, `playwright.config.ts`, `playwright.lifecycle.config.ts`, `vite.config.ts` and `tools/vite/serve-scene-data.ts`: the directory both capture lanes are selected from, the two configs that select them and pin the renderer, port, viewport and per-test bounds, and the preview mount that decides what they are served. It is not the whole of `tools/`, because the verdict chain never runs the other lanes and a digest that covers them would refuse a run for a change that cannot reach its frames. Outside it, each for a stated reason: `src/**` reaches the frames only through `dist/`; `data/**` is the scene digest's; `package.json`'s chain order is pinned by a unit case; the Draco decoder served from `node_modules` is bound by nothing. One case reads the chain out of `package.json` and requires every `--config` in it to be inside the closure, so adding a lane config without adding it here goes red rather than narrowing the closure quietly.

**The cost of the refusal, stated for the coordinator.** A run begun by a wrapper older than this check carries no `harness` key and is refused at `--end` rather than certified without it. That is deliberate — a certificate without a harness binding is the defect — and it means this landing must not reach `main` before the capture in flight has certified, since that run's `--begin` was the older wrapper. The wrapper's own `--end` step is re-read from disk when it runs, so a merge mid-run would refuse three hours of frames.

**Red controls, three of them.** The pre-fix state is one line: `await assertHarnessUnchanged(...)` removed from `certifyVisualRun`. Under it `npx vitest run test/visual-instrument.test.ts` exits 1 with 2 of 39 red — `Error: certification succeeded, and this case exists because it must not: a run whose harness moved during capture was certified.` and `AssertionError: promise resolved "undefined" instead of rejecting`. The other two places the binding can go missing are pinned separately, because the synthetic runs used by every other case write their own `run.json` and would stay green while every real run failed hours later at `--end`: deleting the pin from `beginVisualRun` fails `-t "pins that digest into run.json"` with `run.json written by --begin must carry a harness digest: expected undefined to be defined`, and commenting out the presence check fails `-t "pinned no harness digest"` with `expected [Function] to throw error matching /pinned no harness digest/ but got 'Cannot read properties of undefined (…'`.

The case count moved for a real reason: `31 cases` in `gate-proofs.md` and in round 31's review is now **39**, and the full unit gate is 56 files / **409 tests** (from 401). `AGENTS.md`'s "Five of the instrument's own checks have been made to go red" is now six, and the certificate's contents sentences in `AGENTS.md` and `docs/policies/local-rules.md` name the harness digest.

## B3 — the pointer half was described more strongly than it was driven

**What was believed.** That the freeze-time change to `hero.spec.ts` and `style-picker.spec.ts` drove the World style control "by a real pointer and keyboard", as `plan.md` records it, because the old `locator("option")` / `toHaveValue` pair had been replaced with the shipped control's own `data-style-id`.

**What was false.** `click()` followed by `Home`/`End` and `Enter` cannot distinguish "the pointer opened the listbox" from "the pointer did nothing". `move()` in `src/ui/style-picker.ts` ends in `if (open) render(); else choose(option.id)`, so a **closed** control commits as the active option moves: the arrow key alone commits the style, and the browser's default mousedown focus lands on the button even with the pointer handlers deleted. The option-text assertion did not cover it either, because `allTextContents()` does not require visibility. Round 27 had already recorded pointer-completed selection as unestablished for the control this one replaced (`reviews/27_implementation.md:13`), and round 31 found the new specs had inherited the same shape.

**What landed.** `tools/visual/style-control.ts` finds the rows and the description through the control's own bindings — `aria-controls` and `aria-describedby` — instead of matching every `[role="option"]` on the page, which is the second loss the review named; the description assertion is visible as well as textual, which is the third. `hero.spec.ts` now drives one direction with a real press on the control followed by a real press on the option row, asserting `aria-expanded="true"` between them, and the other direction by keyboard alone (`Enter` opens, `End`/`Home` walks, `Enter` commits), each as its own switch with its own assertions; the same-document return switch became a proper keyboard switch in the other direction, so both paths complete real changes. `style-picker.spec.ts` gets the same pointer sequence and the same scoping.

**The capture's frame set is unaffected in shape.** The eight hero frames keep their names, the two sweeps are untouched, and the style-return frame is still one per time of day; only its direction flipped, so it is now `return-cartographic-*.png`, which the certificate does not read (the 44 are hero + sweep, and the returns are extra flow evidence). The loop's capture order flipped with it. The run costs one more real style application per time of day, because the direction that used to be a no-op re-selection is now a switch; the hero budget is 105 minutes against about 50 minutes of measured captures, so this is inside it, and the next capture is where it gets measured rather than assumed.

**Red control, five arms in 23.1 s.** The hero spec cannot be run while the capture holds port 4319, so the probe is `artifacts/gate-fixes/probe/control-probe.spec.ts` on `playwright.probe.config.ts`: it builds its own page with `page.setContent` — no server, no port, no renderer — and loads the shipped module twice, once as shipped and once with `control.addEventListener("click", onControlClick);` deleted. That mutation is the review's own hypothetical and it is in the *subject* rather than in the check. Shipped + new sequence: passes. Shipped + old sequence: passes. Dead pointer + new sequence: fails by name, `a pointer press on the World style control must open its listbox`, `Expected: "true"`, `Received: "false"`. Dead pointer + old sequence: **passes**, which is the defect stated as a measurement — the old assertion was not wrong, it was blind. Fifth arm, added with `b152da5`'s assertion messages: the list is opened by a real press and no option is pressed, and the commit assertion fails with `the press that opened the list must be what commits the style`, `Expected: "cartographic"`, `Received: "satellite"`, the control still reading `aria-expanded="true"` and `data-style-id="satellite"` in the call log — opening the list is not what changes the style. The probe prints arms 3 and 5 rather than swallowing them, and passes only because those failures are the expected ones.

**One bound worth stating, because it is easy to overclaim.** The pair cannot see a *spec* that swaps its option press for a key press: `choose()` is the one place the pointer and keyboard paths meet, so the app's state after a commit is identical whichever path produced it, and no assertion over that state can distinguish them. What the gate owns is that the row press is reachable and is what commits, and that the press opening the list is the pointer's. Keeping the spec's pointer arm pointed at the option row is a review property, not a checked one.

**What was checked on the real thing.** `npm run build` (1.59 s) and `npm run visual:smoke` in the worktree: **1 passed (59.2 s)**, on SwiftShader, on the production build, exercising both style directions through the shipped control including a pointer press on the option row. `style-picker.spec.ts` itself ran green (306 ms) on a probe config with a dead base URL, because the spec fulfils its own fixture route and never needs the verdict lane's server. The first run of that probe found a real defect in the new helper: `row.locator("[data-style-id=…]")` searches *inside* a row, and the attribute is on the row, so it resolved to nothing and the click waited out a 60-second timeout. It is scoped from the listbox now. That is the whole reason for running an edited spec rather than reasoning about it.

**Bounds.** The probe covers the DOM control's own input path: one module, two registry entries, one initial style, no app and no pixels. It says nothing about `hero.spec.ts`'s own assertions, which only the capture run can produce, and nothing about the app beyond what `visual:smoke` reaches. The smoke lane does not assert `aria-expanded`; the hero spec's new middle assertion is therefore proven only against the module in a fixture, which is the same module the app ships and the same code path the smoke lane's press enters.

## The mis-citation

`src/ui/style-picker.ts:12` cited `reviews/30_implementation.md` for the native-select reachability measurement. Round 30 is the paint round and never carried it; round 27 did, at `reviews/27_implementation.md:13`, with its probe preserved under `artifacts/style-ui/scratch/select-probe/`. The comment now cites round 27. The probe path is *not* written into the source: it is ignored scratch that reclamation deletes when its task closes, and a citation to a file that will not exist is the same defect one step later. Checked rather than assumed: the built bundle is byte-identical with and without the edit — `dist/assets/index-DQRj4aHc.js`, SHA-256 `A4F3A5085F7F4C79344A91933054EC649C03C8EB220B2C7C7C73CD3D2616F577`, built twice in the worktree — so this comment change cannot move any build-bound evidence. Only the `.js.map` differs, and `beginVisualRun`'s file filter is `/\.(js|css)$/`, which does not match it.

## A self-inflicted defect worth recording: the tooling here is Windows PowerShell, not PowerShell 7

Filling the landed commit sha into `docs/learning/gate-proofs.md` was done as `(Get-Content -Raw) | Set-Content -Encoding utf8`. That shell is **Windows PowerShell 5.1**, whose `Get-Content` decodes a BOM-less file through the ANSI code page, so the UTF-8 bytes of every em dash, curly quote, multiplication sign and tick were read as two or three Windows-1252 characters and written back as UTF-8: **240 characters double-encoded**, 80 `â€` sequences where the file had 58 em dashes and no damage, and it was committed that way in `4a7448d`. Nothing in the gates could see it: it is a tracked document, so no test reads it, and the round-31 review that read the previous revision would have read this one as mojibake.

The repair is exact rather than a retype, because a round trip through Windows-1252 is reversible: every byte 0x00-0xFF has a code point there, so mapping each code-page character back to its byte and decoding the result as UTF-8 restores the original. `artifacts/gate-fixes/probe/repair-encoding.mjs` does that, refuses to write if the result contains a replacement character, and reported `240 code-page characters folded back to UTF-8`. The check that it worked is the diff against the same file's parent blob: 59 insertions and 2 deletions, exactly the two new entries and the two lines they amend, against 151/94 for the damaged commit.

The rule for this repository: **write tracked files with the editor tool, or with Node.** Do not round-trip a UTF-8 file through `Get-Content`/`Set-Content`/`Out-File` here, and do not use them to substitute text in a document whose prose is not ASCII — the failure is silent, it survives the commit, and the only instrument that caught it was comparing the file against its own git blob.
