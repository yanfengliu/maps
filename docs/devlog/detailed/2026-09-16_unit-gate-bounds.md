## The unit gate was red for two reasons, and neither was the product

**Timestamp:** 2026-09-16 19:45–20:40

**Action:** the assignment was one flaky file, `test/visual-evidence.test.ts`, on a machine at a measured 100% of its 32 logical cores (24 physical) from a sibling `3d-maker` checkout's Vite server and browser suites. Diagnosing it turned into two independent failures of `npm test`, and both are fixed here:

1. **The bounds did not describe the work.** `test/visual-evidence.test.ts`'s two cases ran on Vitest's 5000 ms default. Each now carries a ceiling derived from what its own case does, the file's header says which applies to what and why, and a third case checks the derivation. `test/visual-instrument.test.ts`'s four frame-set groups carry the same derived ceiling, because they pay the same cost.
2. **One case starved the runner's RPC.** `npm test` exited 1 on runs in which every test passed, with `Errors 1 error` naming `[vitest-worker]: Timeout calling "onTaskUpdate"`. The trigger was `test/pedestrian-overlap.test.ts`, one synchronous case running 60,000 ticks; the tick loop now turns the event loop every 2,000 ticks.

**Result:** `test/visual-evidence.test.ts` alone, both before and after: `2 passed`, 4.70 s wall, cases at 458 ms and 2,881 ms on the loaded box. Inside the loaded suite before the fix, the same file cost 10.06 s with both cases dead at 5000 ms. After the fix its three cases measured 6,143 ms, 13,940 ms and 3,779 ms across three full runs, all green.

The phase probe (`artifacts/flake-probes/phase-timing-probe.ts`, never committed) attributed the first case's cost to `beginVisualRun`'s `sceneTreeDigest` over the served scene — **2,185 ms** for 84 files and **214,114,015 bytes** with every core held, against **425-447 ms** for the same call over the earlier 371 MB payload on an idle machine — plus 91 ms for the harness digest. It attributed the second case's to **88 `decodePng` calls of 921,600 pixels each**: 21 ms a frame quiet, 956 ms for 44, 2,877 ms for a full `verifyVisualRun` pass. The fixture write is 818 ms. Neither cost is removable from a test file: `beginVisualRun`'s mounts are module constants rather than a parameter, and the 88 decodes are what `verifyVisualRun` does over the two accepted passes that stop the four refusal assertions from being satisfied by a function that throws at everything.

The exit-code failure was reproduced live and named from Vitest's own source. `createBirpc` arms a `setTimeout` of `DEFAULT_TIMEOUT = 6e4` on every worker-to-runner call (`node_modules/vitest/dist/chunks/index.B521nVV-.js:3`), and `onTimeoutError` in `chunks/rpc.-pEldfrD.js:48` throws `[vitest-worker]: Timeout calling "<method>"` when it fires. It fired in three of three runs at the default worker count — 19:53, 20:02 and 20:12 — and in each run the log's own next line after `test/pedestrian-overlap.test.ts` finished is the unhandled error. That case is a synchronous `it()` over 60,000 ticks, measured at 92.9 s, 57.1 s and 47.6 s in those three runs, so its worker never reaches Node's poll phase inside the deadline and the runner's reply to an outstanding call waits in the queue until the overdue watchdog has already fired.

**Reasoning:** the two failures have different fixes, and the second one's obvious candidate was wrong.

The file's timing dependence cannot be removed inside the file, and the alternative — a `mounts` parameter on `beginVisualRun`, or a scene-root override — is a change to `tools/visual/**`, which is frozen while a capture may start and is itself bound into the certificate's harness digest. So the honest move was the one the repo's own `tools/visual/budget.ts` takes for the capture specs: name the ceiling in the file's header, derive it from the work, and make the derivation checkable rather than a sentence. The ceiling is a literal 60 s with a case that binds it, not a computed product, for the same reason `budget.ts` writes `HERO_CAPTURE_ALLOWANCE_MS = 9 * 60_000` and lets `test/visual-budget.test.ts` bind it to the recorded pace: a bound computed from the same constants it is checked against proves only that the code agrees with itself.

For the watchdog, bounding worker concurrency was tried first, as the cheapest candidate. It was **rejected on measurement**, not on taste: with `maxWorkers` at half the logical cores (16), the 20:12 run still tripped the watchdog immediately after the same 92.9 s case, and peak node processes only fell from 100 to 48 against 32 logical cores. `vitest.config.ts` is therefore unchanged. What the three firings have in common is a worker that cannot turn its event loop, so the fix belongs in the case: `YIELD_EVERY_TICKS = 2_000` is a turn every 1.6-3.1 s at the measured pace, a nineteen-fold margin against the 60 s deadline even if the machine ran ten times slower. The population is stepped with a fixed `STEP` and the tick's own simulated time, never the wall clock, so the turn cannot change a number this gate reports — that is the property that makes this a courtesy to the runner rather than a change to the measurement, and it is stated in the file's header as an assumption rather than as something this gate checks.

**The unit's own check was self-satisfying, and its own mutation caught it.** The first version of the case that verifies each case runs on its ceiling searched the file's source for the literal string `{ timeout: EVIDENCE_BUDGET_MS }` — which appears in that check's own body — so deleting the option from the case left the check **green**. It now builds the needle and asserts the occurrence count is 1. The reviewer's own session found two checks of the same class in the human-set lane, so this is a pattern rather than a slip: a check that can find its own needle, or that reads a malformed value as "nothing recorded", reports a pass it did not earn.

**Notes:** the three final runs are three runs; they cannot prove a race is gone, and the entry says so. What is proved is the mechanism (a worker that cannot turn its event loop against a 60 s deadline) and that the case which triggered it no longer holds the loop for more than a few seconds. `test/pedestrian-overlap.test.ts`'s own header now carries that reasoning, because a later session that "optimises" the yield away would reintroduce exit 1 on a green run and would have no way to know why. The `visual-instrument` groups share one ceiling across four groups, so a case inside one that pays none of the cost is bounded loosely; it finishes in milliseconds either way. Finally, the 44-frame decodes and the scene digest are the visual certificate's own work being paid by the unit gate; a `mounts`/`roots` parameter on `beginVisualRun` would let the unit cases point at a synthetic tree and remove it entirely, and that change lives in the frozen harness rather than here.
