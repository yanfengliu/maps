# Defect register

## 2026-09-08 — navigation hangs while disposing a refined city

Observed symptom: the hero capture could render its dusk views, then navigation to noon stalled while leaving the page. Removing selected disposers changed the failure, but omitting cleanup was not an acceptable fix. The diagnosis isolated the actual `3d-tiles-renderer` LRU path: fractional mipmap estimates accumulate and subtract in different orders, leaving a positive remainder after every item is removed. The removal loop then has no item left to advance it.

Repair: wrap the existing tile byte estimator with `wholeByteAccounting`, taking a conservative integer ceiling per tile. Every ordinary disposer remains active. `test/tile-memory.test.ts` exercises the actual upstream zero-budget unload in a child process: the reintroduced fractional control times out after two seconds; repaired accounting removes all three items and returns zero. `tools/visual/lifecycle.spec.ts` drives both styles and crossing/approach camera poses through normal controls, then navigates to noon with a 15-second navigation bound. The repaired sequence passed in 36.5 seconds during candidate 2. The child proof covers the reordered fractional accounting class; the browser sequence covers that loaded navigation path, not every possible unload or device. Annotated 2026-09-15: that 36.5 s run recorded neither its rasteriser nor the scene it drew, and no raw record of it was found, so it cannot be read as evidence that this check passes on SwiftShader today; see the 2026-09-15 entry below.

Tests cover duplicate frames, translation, radius, inconsistent pose metadata, epoch/counter regressions, real upstream damping and measured stall/total time. ## 2026-09-15 - navigating away from the refined city stalls about 28-30 s on a software rasteriser

Observed symptom: on a machine drawing with SwiftShader, leaving the refined city for another URL freezes the page for roughly half a minute before the replacement document starts. The 15 s navigation bound in `tools/visual/lifecycle.spec.ts` fails, and the user-visible effect is the same stall.

Investigation: an init script timed the application's own `pagehide` listener on the absolute page clock while a stage localisation and three probe arms measured where the interval sits. The application's cleanup (`picker.dispose()` plus `app.dispose()`) spans 2.4 ms with no context loss, 4.3 ms of app work when `WEBGL_lose_context.loseContext()` is forced inside `pagehide` (that handler then spans 30,453 ms), and 2.1 ms on the hardware arm. The replacement document's own document-start script does not run until +27.87 s, and the stage localisation showed the wait failing at 15,016 ms even with `waitUntil: "commit"`. On the hardware renderer the same unchanged check navigates in 32-110 ms.

Root cause: Chromium's destruction of the outgoing page's WebGL resources on the renderer main thread under SwiftShader. The mechanism - deleting resources versus draining in-flight work - is not separated by this evidence, and the cost is not shown to be independent of the scene's resource count (the 2026-09-13 trace of the same failure recorded 65 loaded tiles, `cachedBytes` 630,155,033, `gpuBytes` 317,190,172). The application's own cleanup is excluded as the cause; it is milliseconds in every arm.

How it is checked from now on: the lifecycle check runs on the hardware renderer the deliverable targets (`playwright.lifecycle.config.ts`, part of `npm run visual`), records the unmasked renderer string each run, and fails by name if that string names a software rasteriser. A machine with no usable GPU reports the check unavailable and red - never a skip and never a pass. The software baseline stays reproducible as disclosed counterevidence through the ignored diagnostic config and the preserved trace, and this bound must be re-measured when the scene changes materially.
