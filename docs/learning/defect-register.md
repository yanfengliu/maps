# Defect register

## 2026-09-18 — the flicker judge read byte offsets with pixel indices, so every changed-pixel fraction was computed from the wrong byte and RUN-01 published the result

Observed symptom, from RUN-01's own record (`artifacts/flicker/RUN-01-REPORT.md`, `2cdc349`): `changed` read **exactly 1.0000 on six of nine orbit pairs** and 0.6254-0.6859 on the rest, while the pairs were 6-8 rendered frames and a ~30 px picture move apart. RUN-01 read that as its own estimator failing and wrote the arithmetic to match — "a correct alignment leaves smooth dusk gradients well under 8/255, so a true 100%-changed reading is not reachable", which is reasoning from the number rather than checking it. The number was not reachable for a different reason.

Investigation, after RUN-02's cut of the gesture brought the motion inside the estimator and `changed` moved only from 1.0000 to 0.9703. A standalone recount of the same two PNGs at the judge's own estimated shift gave 0.1871. `channelDelta` takes **byte** offsets and its caller `comparePair` passed **pixel indices** — the `* 4` was missing on both arguments — so every "delta" was a byte read at a quarter of the intended position. It did not throw: a 1280x720 frame's RGBA array is 3,686,400 bytes and its pixel indices only run to 921,599, so every read landed *inside* the buffer. `Uint8Array` returns `undefined` past its end anyway rather than throwing, `Math.abs(undefined - undefined)` is `NaN`, and each of the three comparisons in the ternary is false, so the function fell through to the last channel's byte and returned a pixel value as a difference. Reproduced by mutation: calling it with pixel indices again gives `changed pixels were counted at the wrong byte offset: 0.9813 of the frame` against the correct 0.187.

Root cause, and the part that generalises: **a missing unit conversion that every unit fixture in this repo is structurally unable to reach, because their frames are too small to index out of bounds.** The judge's synthetic frames are 192x108 — 82,944 bytes of RGBA — so no pixel index can leave the array and the bug is unreachable there by construction; the lane's real frames are 1280x720 and it is reachable on every pair. The test that would have caught it is one that runs the predicate at the size the instrument actually captures, which the judge now has.

What it invalidates: **RUN-01's `changed = 1.0000` is not a misalignment measurement and must not be read as one.** RUN-01's other diagnosis stands on its own — the gesture moved the picture 30-35 px against a ±12 px search, an estimator failure demonstrated independently by a ±80 px hand search and a monotone flat cost curve, neither of which touches `channelDelta`. The two are separate findings and the corrected record says so. `crawl` is unaffected: it is `countUnexplained`, which never calls `channelDelta`, so RUN-01's crawl figures and their reading as an upper bound survive.

Fix: `tools/flicker/judge.ts`, `channelDelta(frame.image.rgba, previous.image.rgba, at * 4, source * 4)`, with the parameters renamed `leftByte`/`rightByte` and the unit stated in the signature's own docstring so a caller cannot guess wrong. Checked from now on by `test/flicker-judge.test.ts` — "counts changed pixels at the size the lane actually captures, not only at the unit frame's size" — which builds a 1280x720 frame and asserts `changedFraction < 0.1` at a known 1 px shift, and by the `passes a moving camera whose frames differ only by the expected shift` case, whose assertion was inverted by the bug: it required `changedFraction > 0.5` on a pure translation, which is a case asserting the wrong number and is part of why nobody looked. It now requires `< 0.05`, which is what a translation that has been shifted back onto itself measures. **Bound:** both cases gate the arithmetic at 1280x720; neither can see a byte-offset error at some other frame size, and the class — a conversion whose wrongness depends on the array being long enough — is only ever caught by exercising the real dimensions. Watched red by reintroducing the defect; the mutation and both messages are in `docs/learning/gate-proofs.md`.

## 2026-09-18 — every flicker frame recorded a simulation step of about minus one hundred and seven billion, because the page clock was measured from the Unix epoch

Observed symptom: both runs of RUN-01 record `tick ≈ -1.07e11` for every frame (`-107382152727` on the orbit run), so `tickGap` was a large meaningless number presented as a measurement.

Investigation: `deriveStep` computed `(performance.now() - performance.timeOrigin) * 60`. `performance.timeOrigin` is **epoch** milliseconds — 1789702869047.3 measured on this machine — while `performance.now()` is milliseconds since navigation (1206.1), so the subtraction measures about minus fifty-six years. The field's docstring documented it as "the step index derived from the page clock" and it was not one.

Root cause: subtracting a wall-clock timestamp from an interval clock. The two are both "milliseconds" and both from `performance`, and nothing about either name says which is which.

Fix, at both call sites: read `performance.now()` once when the capture begins and subtract that, which is the same one-line change for both. Now `tools/flicker/step.ts`, exported so a unit case can reach it — it lived inside `capture.spec.ts`, where only a browser run could have exercised it. Checked from now on by `test/flicker-step.test.ts`, five cases including one that runs the buggy arithmetic as the negative control and pins it to the value RUN-01 recorded. Watched red by restoring the epoch subtraction: `expected -107382172011 to be 60`, which reproduces RUN-01's recorded tick to the digit. The field is documented as a claim about the clock and not a reading of the loop, so the sequence's aliveness still rests on the judge's stalled-render-counter predicate.

## 2026-09-18 — the flicker judge answered "the picture did not move" when the estimator could not follow it, and RUN-01 was labelled clean on four such pairs

Observed symptom: RUN-01's record has `estimatedShift` of `-3…0` px on nine pairs, `0,0` on four of them, and the run's own message says `no failures` — on pairs whose real picture motion it had measured at 30-35 px, against a `SEARCH_RADIUS` of 12.

Investigation: the coarse pass returns its best cell whether or not that cell is on the edge of what it searched, so a search that found nothing and a search that hit its wall both look like an answer. At the boundary the two are indistinguishable by return value from a zero shift — and zero is exactly what the criterion's satisfied case looks like. A pair the estimator cannot model was therefore reported as a pair where the picture held still.

Root cause: a sentinel with no channel to say it was a sentinel. The estimator's only output was the shift, and `0, 0` meant both "the best shift is zero" and "I could not search past here".

Fix: `SEARCH_RADIUS` 12 → 24; the fine pass's window is derived from the coarse grid's own cell (41 px on 1280x720, 7 px on the unit frame) rather than a fixed 3, which was narrower than the grid it was refining and so made "the refine pass reached its edge" true of every correct answer; and a pair whose best shift lands on the search radius now fails **by name** as unmodelable, in terms that separate the two readings in as many words. The crawl figure is still computed and still reported on such a pair — only the failure is suppressed, because a crawl figure under a misaligned shift is a consequence of the estimator and two failures for one cause read as two defects. Checked from now on by `test/flicker-judge.test.ts` — "fails a pair the estimator could not model by name, instead of returning 0,0 as a still picture" — which drives a 30 px-per-frame record against the radius and asserts the message, the pair's name, the shift, the radius and the distinction sentence, and which also asserts the negative half (a shift well inside the search is not refused) so the case cannot pass on a judge that fails everything. Watched red: removing the boundary flag gives `a pair beyond the estimator's search was not refused`. **Bound:** it gates the estimation, not the picture — a pair refused here is one whose crawl figure is not usable, which is the point, and the flag being false does not establish that the shift is *right*.

## 2026-09-18 — the near-field road was still flat after the light was fixed, because the tile put its contrast in octaves a viewer integrates

Observed symptom, on the certificate the dusk fill landed with (`685d0eaeb5669287`, frames preserved at `artifacts/dusk-light/after-arm/`): the satellite `plaza-az000` near-field road — the `near-pavement` rect, 320,540 640x180, the `roads:plateau-tran` mesh — no longer read as black (mean 27.78 of 255, no pixels under 12) and still read as a flat dark fill: **0.304 display levels between neighbouring pixels, 3.580% of albedo, 82.2% of neighbouring pixel pairs bit-identical, 91.0% of the rect indistinguishable from a 3x3 smooth** — against the pavement control in the same frame at 1.604 levels and 5.891%. Opened at 1:1 the crop is a featureless gradient. The previous register entry had named this as the remaining half and predicted the lever: the tile's amplitude, not the light.

Investigation, measured on a scratch probe that drove the certified pose through the real controls and reproduced the certificate to the digit (0.304 levels, 3.580%, 82.2% — so the probe is a ruler and not a second opinion). Raising the *strength* on the shipped spectrum moves the frame slowly: 0.45 → 0.75 is 1.67x strength for 1.46x step, and 0.75 → 1.1 is 1.47x for 1.38x, so the pavement's share needs about 0.9–1.0, and at 1.1 the near field's added contrast is 4 m blotches — the frame reads as oil-stained, not as aggregate. Re-weighting the *spectrum* toward the fine octaves moves it faster: the shipped vector `(0.04, 0.075, 0.175, 0.5, 2, 5.2)` puts 10.30% of albedo between neighbouring texels at mip 0 where the old one put 6.35%, and in the frame it clears the pavement's share at strength 0.72. Doubling only the two finest octaves was tried and does not clear it (5.810% at 0.72), so the full reallocation is what was needed rather than a nudge.

Root cause, and it is a different one from the previous entry's: the tile's **spectrum** was the binding constraint, not its strength. The old vector is dominated by its 1–4 m octaves — the finest lattice carries 1.7 of 11.0 units of weight — so most of the contrast it added sat at a scale the eye integrates at the hero crossing's 0.012–0.03 m/px near field, while the texel-scale content that reads as asphalt was thin. Raising the strength therefore bought blotches before it bought grain. The frame's own measure said the same thing from the other side: at the shipped setting the tile-space step was 6.35% of albedo and the frame showed 3.580%, because the frame integrates the coarse half.

Fix: `src/scene/surface-detail.ts`, the road's octave vector to `(0.04, 0.075, 0.175, 0.5, 2, 5.2)` and its strength 0.45 → 0.72. Measured on the certificate's own bytes (build `index-Dj6sqKQI.js` → `index-DRmtpVMl.js`, runs `685d0eaeb5669287` → `b9d02f80d450203a`, both binding `sceneTreeDigest 1ebda662…` over 117 files / 301,674,209 bytes on the same adapter and driver): the road rect's neighbouring step **0.304 → 0.613 display levels**, its share of albedo **3.580% → 7.241%** against the pavement control's **5.891% → 6.255%** in the same frame, its bit-identical neighbour pairs **82.2% → 54.6%**, and the rect's pixels indistinguishable from flat **91.0% → 61.2%**. The cartographic style moves further because its road albedo is 5.6x: its near band goes 0.706 → 1.837 neighbouring levels and 1.6% → 29.8% of pixels over 2 from the local mean. Whole-frame tone does not move (satellite noon crossing 104.026 in both arms, cartographic noon crossing 155.177 → 155.176, cartographic overhead road sample 115.69 → 115.68) and no frame gains a clipped pixel. **The cost is coarse content** — the tile's 16x16 block-mean spread 44.95 → 19.80 of 255 and the mip-3 step 11.45 → 9.05 of 255 — which is what the trade was: every mip a camera between 0.0144 and 0.0886 m/px resolves measures *higher* than before, and at the overhead framing the road is unchanged.

Checked from now on, with each check's bound stated. `test/surface-detail.test.ts` raises the road's mip-0/mip-1 floors to 0.08/0.045 and adds a case that holds the **shape** of the spectrum: the octave weights must rise toward the fine end by at least 1.2x each, the fine half must outweigh the coarse half by at least 5x, the mip-1 step must stay at or above the 3.97% the previous spectrum gave, and the mip-0 step must exceed 1.5x the mip-1. The strength ceiling rises from 0.5 to 0.8, because the numbers that moved it are the frames: 0.72 shows grain and 1.0 on the old spectrum shows oil. Watched red first twice — the old vector and strength fail the floors naming `6.35% of albedo at mip 0` and `expected 0.06354591245947225 to be greater than or equal to 0.08`, and the old vector at the shipped strength fails the shape case at `expected 2.678571428571429 to be greater than 5` while every floor passes, which is the mutation the previous gate could not see. **Bound:** those cases gate the generated texels, not the pixels; a repeat lattice, aliasing and a surface that reads as noise are only visible in the frame set, which is the 44 certified under `b9d02f80d450203a` with 1:1 crops preserved at `artifacts/grain/crops/` (before/after `near-pavement`, `left-ground` and `right-ground` cells for both styles; the frames in `artifacts/grain/arms/`).

## 2026-09-18 — an `npm ci` through a worktree's `node_modules` junction emptied the primary's dependencies

Observed symptom: a lane went to re-run its gates and found the primary checkout's `node_modules` at **zero top-level entries**, which broke its own worktree and every other worktree junctioned to the same tree at once. `git status` was clean and no tracked file had changed.

Investigation: the worktree convention junctions `node_modules` to the primary, and `npm ci` deletes and rewrites the directory it installs into. Run inside a junctioned worktree it therefore emptied the primary's dependency tree rather than the worktree's. Two lanes were working at the time and both junction `node_modules`; the lane that found it installed into its own worktree and then re-ran `npm ci` in the primary to restore it, which brought back 74 packages / 61 top-level entries with `vite` and `vitest` present. Nothing tracked was touched.

Root cause: the same junction-write class as the two incidents recorded below — the convention is safe for reading and for gates, and a write through it lands in the primary. `npm ci` is the most destructive of the three because it deletes its target wholesale.

Checked from now on: `docs/policies/local-rules.md` carries the rule beside the data rule — a lane that needs to install or reinstall dependencies must not have `node_modules` junctioned; it installs in the primary or gives its worktree a real `node_modules` of its own. The three incidents together (a `data:scene` write, a seven-junction recursive delete, and this `npm ci`) are the case for treating the junction convention as read-only inside every worktree, which is how the rule now reads.

## 2026-09-17 — the detail tile was in the bundle and invisible in the pixels, and the black plaza near field was asphalt rather than light

Observed symptom, from the eight inspection reports under `artifacts/inspection-gpu2/` bound to certificate runId `fb07b11ea3b8296f` (the re-capture after the tile landed in `c0d0f7c`): every ground and road crop in the hero approach frames was unchanged from the pre-tile capture beyond dither, structure energy within 1.2% and whole-frame mean difference 0.004–0.28/255; the cartographic plaza's aimed cell measured **38% less** local structure than before the tile; and the satellite plaza's `az000` near field was **black** — 66.6% of the `near-pavement` crop below luminance 12, 98.3% of 8×8 blocks dead flat — while the same frame's right-hand ground showed a full paving grid and a tactile strip. The reports recorded the leading hypothesis for the first as "the `onBeforeCompile` shader patch may be a silent no-op if its `String.replace` anchor does not match the shader chunk three.js actually compiles", and the second as "the light/falloff or the mip fade", because the same material looked legible on one side of one frame and flat on the other.

Investigation, by measurement.

**The patch is applied, and the hypothesis is false.** All four anchors — `void main() {` in both stages, `#include <project_vertex>`, `#include <roughnessmap_fragment>` — occur exactly once each in three r180's `ShaderLib.standard`, which is what `MeshStandardMaterial` compiles. The positive control is in the frames the reports themselves inspected: the basket-weave paving joints at 0.6 × 0.4 m come from this same patch's `sidewalk` branch, which has no texture and no other source, and they are legible in every capture before and after the tile landed. A patch that had gone silent would have taken those joints with it.

**The tile renders and its contrast is two orders of magnitude short of a display level.** Measuring the shipped bytes gives a mip-0 mean neighbouring-texel step of **0.36% of albedo on the road and 0.40% on the ground** — the inspection's own figures, reproduced independently here — and the renderer's curve (ACES filmic at the style's exposure, then sRGB) turns a relative albedo change of 1% into about 0.36 of a 0-255 level. So 0.36% is 0.13 of a level, and the frames were unchanged because there was nothing to see. Two independent mistakes produced that number. First, the octave amplitudes (1, 0.62, 0.38, 0.22, 0.12, 0.06) over lattices of 4 to 128 cells decay faster than the lattices refine, so the field was a smooth 8 m hill whose local step was 2.3% of its own range. Second, and not recorded in the reports: every texel sampled a lattice cell *midpoint* (`u = (x + 0.5) / SIZE`), so with 128 cells each texel centre landed on `fx = 0.5`, where smoothstep's slope is zero — the finest octave was written as the average of two neighbouring lattice values, halved and smoothed before it was sampled. A further fact makes the regression concrete: the tile commit **removed** the road's previous `grain * 0.025` sine term and replaced it with 0.36%, so the near-field asphalt lost about seven eighths of the structure it had. That is why the cartographic plaza's aimed cell measured 38% less structure after the tile than before it.

**The black near field is the road mesh, and the "position-dependent" premise was a region-labelling error.** The inspection tool names its bottom row `left-ground` and `near-pavement`, and both reports read those names as material claims. They are grid positions. At the plaza pose the camera stands on the avenue, so the near field and the left-hand bottom band are the PLATEAU `tran` road surface (`roads:plateau-tran`), and the paving grid that reads as healthy is the pavement mesh on the right (`roads:plateau-semantic-pavement`) — 0x32363c against 0x999991 in the satellite style, a tenfold albedo difference between two meshes drawn in one frame. Measured from the frames for this entry: satellite near-field road median 10.4 and 66.6% under 12 (reproducing the report exactly), satellite right-ground pavement median 51.3, cartographic near-field road median 52.4. Light cannot be the mechanism: `lighting.ts` stops the key light casting shadows below 8 degrees of solar elevation and this preset is at −3.9, so no shadow exists that could fall differently across one horizontal plane; and the road mesh's stored normals are 100% upward-facing, measured, so it is not a flipped-normal surface lit from below.

Root cause, in three parts. The tile's generator had no bound on the quantity that decides visibility — the neighbouring-texel step in albedo, which is the tile's local step times the shader's strength — so a change that satisfied "carries structure at more than one scale" shipped invisible and its own unit cases were green. Second, the sampling offset systematically averaged the finest octave away, so the spectrum that was chosen could not have reached the pixel even at a higher strength. Third, the inspection's own region names were read as materials, which turned a two-mesh albedo difference into a search for a light falloff that does not exist; the road's near-black albedo (linear 0.032, below the range asphalt occupies at all) is the whole of that defect.

Fix: `cd94f1a` (the tile's spectra, corner-aligned sampling, anisotropy 8, and `patchSurfaceShader` extracted as a pure function that refuses a source missing an anchor) and `a2282f8` (the satellite road's albedo 0x32363c → 0x474d55). (2) The crowd leg's opening frame records camera `(462.439, 17.232, 442.423)`, target `(459.056, 15.200, 416.724)`, `azimuth` 0.1308997 and `distance` 26.000001; the camera sits 26.0000 m from that target at a target-to-camera bearing of exactly 0.1308997 rad. So the flight's own camera is `CROWD_TARGET + (sin, cos) * 26` at `CROWD_AZIMUTH`, 53.1 m from `CROWD_CAMERA`, and `CROWD_TARGET` - not `CROWD_CAMERA` - is the point the flight pans to, which the approach's and crowd legs' own records confirm (their targets land 0.4-1.3 m from it, inside their own pan residuals). Root cause: one number with two meanings, and the file that hands it from one to the other documented the wrong one.
